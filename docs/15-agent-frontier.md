# Agent 前沿：从会回答，到能执行与验证

假设你让助手把一个练习页的“3 + 4”答案改成7，再实际点击“下一题”并检查手机排版。前沿图解的“明确目标→规划与分工→调用工具→验证与修正→保存与交付”，就用这项虚构任务区分各环节。本章的目标：读完一条“新智能体”消息后，能说清它改进了哪一层、怎样工作，以及用什么证据判断任务完成。

先修：[LLM 与 RAG](chapters/11-llm-and-rag.md)、[Agent 基础](chapters/12-agents.md)。版本动态见[网站「Agent 前沿」](https://zray0529-a11y.github.io/computing-learning-hub/#frontier)；本章保留稳定的理解方法。

本章示例均为虚构学习项目，不连接真实账户、模型或付费 API（供程序调用的服务接口）。产品事实核验日期：2026-11-16；入门说明于2026-11-17修订，未以文字修订冒充一次新的产品核验。

## 先判断：这条消息说的是哪一层

| 层次 | 主要职责 | 学习网页例子 |
|---|---|---|
| 模型 | 根据输入生成内容，提出工具调用或下一步 | 判断错字可能在哪一段 |
| Agent 智能体 | 围绕目标，结合状态、工具结果与反馈继续行动 | 查文件、修改、检查，再决定是否完成 |
| 运行框架 | 提供会话、工具执行、权限、任务恢复等基础设施 | 执行命令，保存状态，限制可访问目录 |
| 应用产品 | 将能力包装成可使用的界面和服务 | 让读者提交请求、预览并确认结果 |

这些是教学上的职责划分，实际产品可能同时覆盖多层。Anthropic 用“预定义流程”和“模型动态选择步骤”区分工作流与 Agent，提供了一种工程视角。[官方解释](https://www.anthropic.com/research/building-effective-agents)

换了更强的模型，不代表已经接入浏览器；装好运行框架，也不代表工具拥有账户权限。阅读发布说明时，先找清楚能力由哪一部分提供。

## 六类值得持续关注的能力

### 1. 长任务：中断以后怎样继续

问题是一次对话结束后，未完成工作是否还能接着做。教学上可把进度、证据和下一步写入任务状态，恢复时先检查实际环境。

例如生成学习网页时，已完成正文，但图片检查失败；下一次应从失败处重新核对，而不是把整项任务重复执行。

Managed Agents 将执行环境与会话历史分开，是可以研究的真实设计。长时间运行仍需预算、停止条件与验收；持续运行本身不证明任务有效。[官方架构说明](https://claude.com/ja/resources/articles/self-hosted-claude-managed-agents)

### 2. 协作编排：把哪些事情交给谁

协调者可以拆解目标、分派工作，再综合结果。Fable 的官方说明区分顾问与协调者：前者帮助处理难题，后者可以向其他模型委派任务。[官方模型说明](https://www.anthropic.com/claude-fable-and-mythos-5-2)

虚构例子中，错字核对与图片说明检查可以独立进行；修改页面与验证修改结果有先后关系，不能随意并行。

多 Agent 与长任务演示说明某种方案在特定条件下可行。实际收益要比较完成质量、返工、时间与成本，不能由角色数量推出。

### 3. 工具与电脑操作：让动作得到环境反馈

API 工具通过参数和结果连接程序；电脑操作工具通过截图、鼠标和键盘与界面交互。模型提出调用，应用执行，再把结果送回下一轮。[官方电脑操作机制](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)

例如检查学习网页，助手可以请求打开页面、点击“下一题”，再观察题目是否实际变化。点击请求与点击成功是两条不同证据。

工具可用范围依赖具体产品、接口和环境；有视觉理解能力，并不意味着已经获得电脑控制权。每步都应核对当前页面与允许的动作范围。

### 4. 上下文与记忆：保存什么，怎样重新找到

当前上下文是这一轮可使用的信息；任务状态记录做到哪一步；资料库保存可检索的知识。把它们分别命名，才容易发现信息缺失在哪里。

DeepSeek 原型使用 SQLite 保存触发事件、任务、决定与消息回执。这是可追踪的工作状态，并不等于模型进行了新的训练。[官方持久化设计](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/007-architecture.md)

例子：保存“已修复标题、尚未检查手机页面”，比只保存“任务进行中”更有恢复价值。过时状态必须对照当前文件重新核实。

### 5. Skills：把工作方法做成可复用材料

Agent Skills 用包含 SKILL.md 的文件夹组织操作说明，也可附脚本和参考材料；支持它的助手可以按任务读取。[标准与维护方式](https://www.anthropic.com/news/donating-agent-skills-to-the-agentic-ai-foundation)

例如建立“学习网页检查”技能，说明怎样核对题目、手机排版与链接。它像操作手册；类比的边界是，手册不会自己执行，也不会自动取得权限。

复用时还要确认工具、文件路径与依赖是否适合新环境。说明文件写了“已检查”，不能替代实际运行与观察。

### 6. 验证与权限：把完成条件写在动作之前

先定义完成证据，再限制行动范围。运行记录回答“发生了什么”，验收条件回答“是否达到目标”；两者都需要。

DeepSeek 原型把待回答、待审阅和执行失败列为不同状态。这样的区分有助于避免把“交给人处理”误报为“全部完成”。[官方任务状态](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md)

例子：改完一道题后，检查答案数值、按钮行为与手机阅读效果。验证失败就修正或说明阻碍；权限变化由执行系统落实。

## 一个便于复用的教学架构

以下是本教材的教学归纳，用来组织概念；它不代表任一厂商未公开的内部实现。

| 环节 | 输入与产物 | 需要问的问题 |
|---|---|---|
| 定义目标 | 请求、范围与验收条件 | 怎样才算做好？ |
| 规划与路由 | 可执行步骤、必要的子任务 | 哪些能独立做，哪些有依赖？ |
| 执行与工具 | 文件、命令、页面操作及返回结果 | 动作真的执行了吗？ |
| 状态与证据 | 已完成步骤、来源、错误和待办 | 重启后怎样避免漏做或重复做？ |
| 验证与交付 | 对照验收的结果、剩余限制 | 完成、继续修正，还是需要人判断？ |

这不是只能走一次的直线：验证发现问题时，回到相应步骤；运行环境变化时，先重新核实状态。重试涉及外部写入时，还应学习[幂等与失败恢复](chapters/09-distributed-systems.md)。

## DeepSeek SuperAgent：用公开原型看具体机制

官方组织公开的 dsh-superagent-prototype 面向单个 GitHub 仓库，可选接入飞书。README 将它定位为研究原型，明确说明部分设计文章方向尚未实现。[原型说明](https://github.com/deepseek-ai/dsh-superagent-prototype)

可以沿着公开文档追踪四件事：

- 来源产生事件：消息、评论等进入系统，相关上下文与已有任务关联。
- 规则判断请求：事件是否构成新工作，需要经过授权规则判断；读到消息不等于获准执行。
- 任务进入执行：每项获准任务有自己的执行会话与目录，主会话负责协调。
- 结果回到来源：执行者报告进度、问题或可审阅结果，必要时等待人的后续输入。

上述流程依据[领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/001-domain.md)与[执行说明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/003-execution.md)。学习重点是事件、授权、任务与状态的连接，而非给一个模型增加“超级”称号。

原型的独立目录不等于系统级隔离。官方部署文档说明，相关会话使用操作者的系统权限运行；真实部署需要单独考虑环境与凭据边界。[部署说明](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/main/docs/006-deployment.md)

## 虚构演练：修复学习网页并验证

先预测：如果助手说“代码已改好”，你还缺哪几类证据？再阅读以下演练。

> 请求：修复练习页上“3 + 4”的答案显示错误，让“下一题”按钮可用，并检查手机页面。只修改这个练习页，交付可预览结果。

1. 定义验收：答案应显示 7；点击后切换题目；窄屏不遮住题干和按钮。这里只是虚构验收目标，尚未执行。
2. 收集证据：读取相关文件并复现问题，记录当前页面行为；先确认原因，再决定修改范围。
3. 安排工作：答案逻辑与样式检查可分别调查；涉及同一文件的修改要协调合并，最终验证等待修改完成。
4. 执行修改：工具写入文件，保存变更记录；将实际错误与执行结果写入任务状态。
5. 核对结果：运行相关逻辑检查，实际点击按钮，观察手机视口；测试通过不能替代未覆盖的页面检查。
6. 交付证据：提供预览、变更说明与实际检查结果；仍失败的部分说明原因与下一步。

教回时请指出：模型负责了哪些判断，工具执行了哪些动作，运行框架保存了什么，最后是谁根据什么条件决定完成。

## 费曼式自测：先说给没有编程基础的人听

- 问题一：模型、Agent 与运行框架怎样配合？请用修复练习页解释，不只背术语。
- 问题二：两个执行者都说“答案正确”，为什么仍然需要验证？
- 问题三：一次任务跨设备继续完成，能证明模型获得了永久记忆吗？

先闭卷作答，再对照以下答案；能照读不等于能迁移到新例子。

- 答案一：模型提出判断和动作；Agent 围绕目标反复利用结果；框架提供工具执行、状态与权限等支撑。最终要看到实际网页变化。
- 答案二：它们可能共用错误材料或漏掉同一情况；应检查真实数值、交互和目标条件，而不是只统计赞同次数。
- 答案三：不能。会话和文件可能保存在服务端，另一设备重新读取；这说明状态可恢复，不直接说明模型权重改变或记忆永不丢失。
