# 08 软件工程：让变化可理解、可验证、可恢复

## 核心判断

软件工程管理的是持续变化中的正确性与协作成本。代码生成更快以后，“问题是否定义对、结果是否可验证、出了问题如何恢复”仍需要明确设计。

先修：[编程](03-programming.md)、[数据库](07-databases.md)。本章用“过期观察不能当作当前事实”贯穿说明。

## 从一句需求走到可检查的契约

“显示最新状态”至少有四个未回答的问题：最新是采集时间还是入库时间？多旧算过期？没有观察如何表示？客户端是否可以看到证据？

把需求改写为可观察规则，例如：“仅当观察年龄在 0 到 600 秒之间时显示状态；超过期限显示未知；未来时间戳不能直接通过；保留采集时间供用户判断。”600 秒在此是教学参数，实际产品应由业务和采样频率决定。

契约包含输入、输出、异常和不变量。不变量就是无论经过哪些步骤都必须成立的条件，例如“没有有效证据时不能标成已确认”。接口契约也应说明字段类型、可空性、时间单位、错误码和权限。

| 概念 | 含义 | 在本例中的表现 |
|---|---|---|
| Requirement／需求 | 要解决的问题与约束 | 避免把旧观察当实时状态 |
| Specification／规格 | 可检查的具体行为 | 600 秒边界、未知值、未来时间 |
| Module／模块 | 隐藏实现细节的职责单元 | 时间判断与画面理解分开 |
| Dependency／依赖 | 一个部分依赖的外部行为 | 时间源、数据库、模型服务 |
| Test／测试 | 用样例检查实际结果 | 边界、错误、重试后的结果 |
| Regression／回归 | 改动让原本可用的行为坏掉 | 修改过期逻辑后误认未来时间 |
| Deployment／部署 | 把可运行版本交给环境 | 版本、配置、依赖一起追踪 |
| Rollback／回退 | 恢复到可接受的状态 | 应用回退还要考虑数据格式兼容 |

## 建筑类比的帮助与边界

需求像任务书，接口像专业提资，测试像分项验收，版本记录像图纸变更单。这个类比帮助明确交接条件与责任。

但软件不是一次浇筑后不能改变的实体：同一版本可复制运行，很多错误藏在并发、边界输入和环境组合中；上线后还可能频繁修改。施工图“看起来完整”不能替代运行验证，代码“看起来像对”也一样。

模块划分的目的不是增加文件数量，而是隔离变化。如果每次调整业务规则都要改采集、存储、前端三处相同逻辑，可以把规则收敛到一个有明确契约的地方。反过来，只有十行且不会独立变化的逻辑，不一定值得抽象成框架。

## Git、GitHub、分支、PR分别是什么

Git保存版本历史与分支关系；GitHub是托管和协作平台；commit记录一组版本变化；branch是可移动的版本引用；pull request用于提出和审阅变更。它们解决的问题不同。[Git 官方教材：版本控制](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control)

一次提交最好能说明“为什么改、改后行为是什么”，而不只是“更新文件”。提交成功说明版本被记录，push成功说明远端收到版本；二者都不能证明程序正确，更不能证明已经部署。

小任务的合理节奏是：明确一个行为→做最小修改→检查相关结果→保存可追溯版本。多人同时修改时，应在最新分支基础上合并，保留别人的变更；不要为了省事强制覆盖远端。

## 最小例子：把时间边界写清楚

下面以整数秒演示规则；真实系统还需处理时区、时钟偏差和时间解析。

```python
def usable(observed_at, now, ttl=600):
    if ttl < 0:
        raise ValueError('ttl must be non-negative')
    if observed_at is None:
        return False
    age = now - observed_at
    return 0 <= age <= ttl

cases = [None, 1000, 400, 399, 1001]
print([usable(t, now=1000) for t in cases])
```

预期：`[False, True, True, False, False]`。把判断改成 `age <= ttl` 会让未来时间错误通过；增加 `0 <=` 是在修复具体规则，而不是增加一种装饰性测试。

先自己提出两个能击穿错误实现的输入，再看答案。好的检查应能发现真实错误，不只是重复实现中的每一行。

## 不同检查回答不同问题

| 检查 | 要证明什么 | 不能独自证明什么 |
|---|---|---|
| 单元测试 | 一个函数的边界和规则 | 数据库或服务真的能连接 |
| 集成测试 | 模块之间的契约能配合 | 用户完整流程可用 |
| 端到端检查 | 关键流程能完成 | 所有数据、并发与异常组合都正确 |
| 静态检查 | 类型、语法和部分代码问题 | 业务定义是否合理 |
| 人工审查 | 意图、风险和设计是否合理 | 运行时一定正确 |
| 线上观测 | 实际延迟、错误和使用情况 | 所有未观测路径都没问题 |

对小改动，检查范围跟随具体风险；对涉及数据或权限的变化，要覆盖影响的真实边界。验证完成后应记录实际执行的命令、环境和结果，不把“计划测试”写成“测试通过”。

## AI参与工程时怎样分配责任

模型可以帮助解释、实现、生成边界输入和审查，但需求来源、权限、验收标准与外部事实仍要可追溯。模型给出十个看似一致的答案，不等于有十份独立证据。

一个实用交接包只需包含：目标与现状、允许改动的范围、输入输出契约、完成证据、剩余问题。日志记录变化的理由；测试检查行为；文档帮助下一位接手人找到权威入口。三者各有用途。

代码、配置、数据和模型版本都可能改变结果。可重复实验要同时注明它们，而不是只记录一个提示词。容器也不能自动固定远程服务、网络响应和采样随机性。

## 闭卷检查

1. 为什么“push成功”不能作为功能验收？
2. 一个判断函数只在正常输入上测试通过，还缺哪类证据？
3. 你让AI修改数据格式，前端和历史数据会受到什么影响？
