# 02｜硬件：指令怎样变成真实计算

> **一句话核心：硬件不断取指令、搬数据、做运算，而速度取决于整条路径。**

“换一块更强的显卡”只回答了某个部件能做什么，还没回答整个系统为什么慢。
本章把机器拆成执行、存储与传输三个方面，帮助你判断相机分析、模型渲染和 AI 推理的真实限制。

## 先修与学习目标

先读[计算与表示](01-computation.md)，理解指令和数据都可以编码为比特。
目标是能画出一帧图像从存储或网络进入内存、交给处理器、再保存结果的大致路线。
不必背硬件型号或固定延迟数字；重点是知道该测哪一段。

## 关键术语：沿着数据的路径理解

- **指令集（ISA）**：软件与处理器之间约定的机器指令及可见行为。
- **中央处理器（CPU）**：执行通用指令、处理控制流程的计算单元。
- **图形处理器（GPU）**：适合大量可并行工作的处理器；并非只用于画图。
- **寄存器（register）**：处理器内部直接参与运算的少量高速存储。
- **缓存（cache）**：保存部分数据副本，减少访问较慢存储的次数。
- **内存（RAM）**：承载运行中的程序与数据；常见主存使用 DRAM。
- **持久存储（persistent storage）**：断电后仍能保留数据的 SSD、硬盘等介质。
- **局部性（locality）**：近期使用的数据或其邻近数据，接下来可能再次被使用。
- **延迟与吞吐量（latency / throughput）**：一次任务多久完成，以及单位时间完成多少任务。

## 机制一：存储程序让机器可以换任务

存储程序思想把指令也放进可访问的存储中。
同一套硬件读取不同指令，就能从计算面积切换到解码视频；不必为每种算法重新接线。
这是软件可修改性的基础。[MIT ISA 讲义 §14.2](https://computationstructures.org/notes/isas/notes.html)给出了这一结构。

用简化模型看，程序计数器记录下一条指令的位置。
处理器取出指令、识别操作、取得操作数、执行计算、保存结果，再更新下一条指令的位置。
条件跳转可以改变下一步位置，因此循环和“如果”最终都有硬件上的执行方式。

例如 `total = total + area`，底层可能需要读取两个值、执行加法、再保存结果。
现代 CPU 会用流水线、预测和乱序执行提高效率；“取指—执行”是理解行为的模型，不是说每个部件严格轮流空等。
同样，现代机器可能把指令缓存和数据缓存分开，存储程序也不要求所有物理通路都混在一起。

## 机制二：为什么需要多层存储

如果容量、价格、速度都没有冲突，就不必同时设置寄存器、缓存、主存和 SSD。
现实中，靠近执行单元的存储通常小而快，大容量存储则适合保存更多数据，但访问成本不同。
程序因此要在不同层之间移动数据，不能只看“总共有多少 GB”。

缓存依靠局部性工作：刚访问的相机元数据可能还会再用；逐行扫描图像时，下一批像素往往就在附近。
访问命中缓存，就能较快取得数据；没有命中，则向下一层寻找，并把相邻的一块数据带回来。
机制见 [MIT Memory Hierarchy](https://computationstructures.org/lectures/caches/caches.html)。

缓存不是完整的另一份数据库，也不是无条件加速器。
访问模式很散、工作集超过缓存容量时，命中率可能下降。
因此，相同运算量的程序，仅因数据组织不同，也可能有不同耗时；这将连接到后面的[算法与数据结构](04-algorithms.md)。

还要区分主存与持久存储：程序加载到内存后才能方便地被执行，原始视频通常长期保存在 SSD 或其他存储中。
“硬盘剩余很多”不能保证“运行内存足够”；内存不足带来的频繁换入换出，可能使系统明显变慢。

## 机制三：CPU 与 GPU 为什么各有所长

CPU 通常重视复杂控制流程和单条执行路径的响应，GPU 通常重视大量任务的总吞吐。
对整张图像的许多像素做相似运算、进行大矩阵乘法时，工作容易拆成大量并行单元。
以 CUDA 为例，工作被组织成线程和线程块，由硬件调度；[NVIDIA 编程模型](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)说明了这些组织方式。

但“任务很多”不自动等于“适合 GPU”。
如果下一步必须等待上一步结果，或每个任务走完全不同的分支，可有效并行的部分会受限制。
任务太小时，准备任务、启动计算以及数据传输的成本，可能超过节省的计算时间。

独立显卡通常拥有自己的显存，数据在主机与设备之间移动会花时间；集成或统一内存系统的具体路径有所不同。
NVIDIA 的[最佳实践指南](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)强调减少不必要的传输。
实际选型应测整个业务流程，也应检查显存是否装得下模型、中间结果和批次。

## 机制四：识别瓶颈，才能判断优化上限

假设一帧图像依次经历解码二十毫秒、推理八十毫秒、写结果二十毫秒。
整帧耗时是一百二十毫秒；若只把推理加速十倍，整帧变成四十八毫秒，而不是十二毫秒。
未被优化的部分占据了剩余时间，这正是分析局部加速时必须保留的约束。

对于这条完全串行、其他开销不变的路径，即使推理瞬间完成，仍然要四十毫秒。
因此总加速上限是三倍；这个结论来自当前假设，不是所有视频系统的固定上限。
如果多帧之间能够流水处理，稳定吞吐量与单帧延迟又是不同问题。

可以先问三个问题：执行单元是否忙？数据是否按时到达？是否在等网络、存储或其他任务？
计算受限时减少运算或增加计算资源可能有效；带宽受限时减少搬运和改善数据复用更重要。
这些是需要测量的诊断方向，不能仅靠 CPU 或 GPU 的一个利用率百分比下结论。

## 建筑类比：工人、工作台与材料仓库

寄存器像手边正在操作的材料，缓存像近处工作台，内存像现场周转区，持久存储像大型仓库。
把常用材料放近，可以减少往返；增派工人却不改善供料，工人仍可能等待。
**类比边界：**计算机缓存按硬件规则管理，数据还能复制；材料仓库的物理守恒与人工调度不能直接套用。

这个类比也提醒你：城市模型加载慢，可能是下载、解压、解析、上传显存或绘制中的任何一段。
“模型很大”只是现象，要把它拆成可测的步骤。

## 最小实验：算清局部加速的收益

以下数字是教学假设，并非任何设备的基准测试。

```python
decode_ms, infer_ms, write_ms = 20, 80, 20
before = decode_ms + infer_ms + write_ms
after = decode_ms + infer_ms / 10 + write_ms
limit = before / (decode_ms + write_ms)

print(f"原耗时：{before} ms")
print(f"新耗时：{after:.0f} ms")
print(f"整体加速：{before / after:.2f} 倍")
print(f"理论上限：{limit:.2f} 倍")
```

预期输出：

```text
原耗时：120 ms
新耗时：48 ms
整体加速：2.50 倍
理论上限：3.00 倍
```

再手算：若新增十毫秒的数据拷贝，新耗时是多少？答案应比四十八毫秒更长。
这说明“计算内核更快”和“用户更早看到结果”必须分开测。

## 闭卷检查：先预测，再解释

1. **预测：**把例子的推理再从八毫秒降到四毫秒，整体耗时与原流程加速倍数是多少？
2. **解释：**为什么一台电脑还有大量 SSD 空间，却可能因内存压力而卡顿？
3. **迁移：**相机每秒上传一张小图，云端推理只占总时间的十分之一，应该先测什么？

<details>
<summary>答案要点与常见误区</summary>

1. 总耗时为四十四毫秒，加速约为 2.73 倍；不是上一轮整体速度再翻倍。
2. SSD 与主存承担不同任务，容量不能互相等同；系统可能在频繁搬移当前需要的数据。
3. 先分别测采集、编码、网络、排队、推理和保存的耗时；剩余九成时间决定主要优化空间。

常见误区：GPU 一定比 CPU 快；显存足够就代表系统足够快；单帧延迟等于稳定吞吐量的倒数。
只有在明确的串行处理等假设下，这些指标才可能形成简单对应。
