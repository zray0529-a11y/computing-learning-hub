# 02｜硬件：指令怎样变成真实计算

> **一句话核心：硬件不断取指令、搬数据、做运算，而速度取决于整条路径。**

图解从左侧长期保存程序和文件的持久存储出发，把当前需要的内容加载到中间的主存 RAM，也就是程序运行时的工作区。右侧 CPU 是执行指令的处理器，它用内部的少量高速存储——寄存器——保存当前要计算的数值；结果回到主存，并按需长期保存。
例如分析一帧相机图像，既要取得图像，也要计算和保存判断。“换一块更强的显卡”只改善了其中可能的一段；本章沿着图中的箭头，解释为什么必须关心数据怎样到位。

## 先修与学习目标

先读[计算与表示](01-computation.md)，理解指令和数据都可以编码为比特。
目标是能画出一帧图像从存储或网络进入内存、交给处理器、再保存结果的大致路线。
不必背硬件型号或固定延迟数字；重点是知道该测哪一段。

## 关键术语：沿着数据的路径理解

- **中央处理器（CPU）**：执行通用指令、处理控制流程的计算单元。
- **图形处理器（GPU）**：适合大量可并行工作的处理器；并非只用于画图。
- **寄存器（register）**：处理器内部直接参与运算的少量高速存储。
- **缓存（cache）**：保存部分数据副本，减少访问较慢存储的次数。
- **主存（RAM，通常简称内存）**：承载运行中的程序与数据，便于处理器反复访问。
- **持久存储（persistent storage）**：断电后仍能保留数据的 SSD（固态硬盘）、机械硬盘等介质。
- **延迟与吞吐量（latency / throughput）**：一次任务多久完成，以及单位时间完成多少任务。

## 机制一：存储程序让机器可以换任务

如果换一种计算就要重新接电线，一台机器很难快速从汇总面积切换到分析图像。像施工班组改读另一套操作说明一样，**存储程序**思想把指令也放进可访问的存储中。
同一套硬件读取不同指令，就能从计算面积切换到解码视频；不必为每种算法重新接线。
这是软件可修改性的基础。[MIT ISA 讲义 §14.2](https://computationstructures.org/notes/isas/notes.html)给出了这一结构。

机器接受哪些操作，要由**指令集（ISA）** 约定，例如读数、加法和跳转。用简化模型看，**程序计数器**像指在操作说明上的书签，记录下一条指令的位置。
处理器取出指令、识别操作、取得**操作数**（这一步要处理的值）、执行计算、保存结果，再更新下一条指令的位置。
条件跳转可以改变下一步位置，因此循环和“如果”最终都有硬件上的执行方式。

例如“把当前总面积加上一个房间面积”，底层可能需要读取两个值、执行加法、再保存结果。第 03 章会把这类更新写成程序。
“取指—执行”帮助我们跟踪程序行为；真实处理器可以让多个处理阶段重叠进行，不是所有部件严格轮流空等。

## 机制二：为什么需要多层存储

假设两个房间的面积 `12` 和 `8` 保存在 SSD 文件里，为什么不能让 CPU 直接“拿着文件名做加法”？
就像档案库里的图纸必须先调到工作台，文件中的字节也要经过读取和解释，成为处理器能取得的数值。CPU 的普通加法指令操作数值，不会自行打开一个 SSD 文件、找面积字段并理解单位。

| 图中的位置 | 工作台类比 | 本例做什么 |
|---|---|---|
| SSD 等持久存储 | 保存全套资料的档案库 | 断电后仍保存原文件；通过设备控制器读取所需内容 |
| 主存 RAM | 摊开当前资料的工作台 | 放运行中的程序，以及已经读入、可继续处理的数据 |
| CPU 内的寄存器 | 手边正在使用的尺寸和中间数 | 为当前指令保存少量操作数与结果，例如取得 `12`、`8`，算出 `20` |

在普通电脑的典型路径中，**设备控制器**负责与 SSD 交互，数据先进入主存，再经处理器的存储通路参与计算；控制器像负责收发资料的接口部件。
这个过程不要求一次把整个视频文件都读入主存，可以分批取得当前需要的内容。得到 `20` 后，也要另行安排写回文件，才能作为持久结果保存。

如果容量、价格、速度都没有冲突，就不必同时设置这么多层。现实中，低延迟的处理器内部存储容量有限，大容量持久存储采用不同的访问方式与成本；不能只看“总共有多少 GB”。
**类比边界：**“远近”表示取得数据的代价，不是固定的地理距离；数据可以复制，真实指令的取数路径也不必完全等同于人工搬图纸。

图中省略了**缓存**：处理器附近暂存常用数据副本的小容量存储。它像手边摆放的常用资料，减少反复去工作台深处取数据的等待。
缓存依靠**局部性**工作，即刚用过的内容或相邻内容接下来可能再用：刚访问的相机元数据可能还会再用；逐行扫描图像时，下一批像素往往就在附近。
访问命中缓存，就能较快取得数据；没有命中，则向下一层寻找，通常带回包含目标及邻近数据的一整块内容。
机制见 [MIT Memory Hierarchy](https://computationstructures.org/lectures/caches/caches.html)。

缓存不是完整的另一份数据库，也不是无条件加速器。
访问模式很散、当前反复使用的数据超过缓存容量时，命中率可能下降。
因此，相同运算量的程序，仅因数据组织不同，也可能有不同耗时；这将连接到后面的[算法与数据结构](04-algorithms.md)。

“硬盘剩余很多”不能保证“运行内存足够”。主存紧张时，操作系统可能把部分内容移到持久存储，之后需要它时再读回来；反复搬移就可能导致卡顿。
这个管理机制在[操作系统章节](05-operating-systems.md)继续解释；这里只要分清“资料放得下”和“当前要用的资料取得够快”。

## 机制三：CPU 与 GPU 为什么各有所长

审一个复杂节点，常要根据前一步结果决定下一步查什么；给大量相似网格逐格填色，则容易把工作分开同时做。
前一种像擅长处理复杂流程的审图小组，后一种像按统一规则处理很多网格的绘图团队：**CPU** 通常重视复杂控制流程和单条执行路径的响应，**GPU** 通常重视大量可并行工作的总吞吐。
对整张图像的许多像素做相似运算、进行大矩阵乘法时，工作容易拆成大量可同时计算的部分。[NVIDIA 的 CPU/GPU 设计说明](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/introduction.html)解释了这种侧重。
**类比边界：** CPU 也可以有多个核心并行工作，GPU 也能执行条件分支；不能把两者固定理解成“一名聪明的人”和“某个数量的只会填色的人”。

但“任务很多”不自动等于“适合 GPU”。
如果下一步必须等待上一步结果，或每个任务走完全不同的分支，可有效并行的部分会受限制。
任务太小时，准备任务、启动计算以及数据传输的成本，可能超过节省的计算时间。

独立显卡通常拥有自己的**显存**，用于存放 GPU 正在处理的数据；数据在 CPU 一侧与显卡之间移动会花时间，集成或统一内存系统的具体路径有所不同。
NVIDIA 的[最佳实践指南](https://docs.nvidia.com/cuda/cuda-c-best-practices-guide/index.html#data-transfer-between-host-and-device)强调减少不必要的传输。
实际选型应测整个业务流程，也应检查显存是否装得下模型、中间结果和批次。

## 机制四：识别瓶颈，才能判断优化上限

回到图解的自测：假设一帧图像依次经历解码 `20 ms`、推理 `80 ms`、写结果 `20 ms`。解码是把压缩文件还原成可处理的图像，推理是用已有模型算出判断，`ms` 表示毫秒。
先把依次发生的三段相加，`20 + 80 + 20 = 120 ms`；若只把推理加速十倍，推理变成 `8 ms`，整帧就是 `20 + 8 + 20 = 48 ms`。
未被优化的部分占据了剩余时间，这正是分析局部加速时必须保留的约束。

对于这条完全串行、其他开销不变的路径，即使推理瞬间完成，仍然要四十毫秒。
因此总加速上限是三倍；这个结论来自当前假设，不是所有视频系统的固定上限。
如果多帧能够像流水作业一样重叠处理，例如处理第二帧时保存第一帧，稳定吞吐量与单帧延迟又是不同问题。

可以先问三个问题：执行单元是否忙？数据是否按时到达？是否在等网络、存储或其他任务？
计算受限时减少运算或增加计算资源可能有效；**带宽**（单位时间能传送多少数据）受限时，减少搬运和重复使用已有数据更重要。
这些是需要测量的诊断方向，不能仅靠 CPU 或 GPU 的一个利用率百分比下结论。

## 建筑类比：工人、工作台与材料仓库

寄存器像手边正在操作的尺寸和材料，缓存像近手的常用资料，内存像工作台或现场周转区，持久存储像大型档案库或仓库。
把常用材料放近，可以减少往返；增派工人却不改善供料，工人仍可能等待。
**类比边界：** 计算机缓存按硬件规则管理，数据还能复制；材料仓库的物理守恒与人工调度不能直接套用。

这个类比也提醒你：城市模型加载慢，可能是下载、解压、解析、上传显存或绘制中的任何一段。
“模型很大”只是现象，要把它拆成可测的步骤。

## 最小实验：算清局部加速的收益

以下数字是教学假设，并非任何设备的基准测试。

```python
decode_ms, infer_ms, write_ms = 20, 80, 20
before = decode_ms + infer_ms + write_ms
after = decode_ms + infer_ms / 10 + write_ms  # 只缩短推理这一段
limit = before / (decode_ms + write_ms)  # 推理趋近零时，仍要解码和保存

print(f"原耗时：{before} ms")
print(f"新耗时：{after:.0f} ms")
print(f"整体加速：{before / after:.2f} 倍")
print(f"理论上限：{limit:.2f} 倍")
```

预期输出：

```text
原耗时：120 ms
新耗时：48 ms
整体加速：2.50 倍
理论上限：3.00 倍
```

再手算：若新增十毫秒的数据拷贝，新耗时是多少？答案应比四十八毫秒更长。
这说明“计算内核更快”和“用户更早看到结果”必须分开测。

## 闭卷检查：先预测，再解释

1. **预测：** 把例子的推理再从八毫秒降到四毫秒，整体耗时与原流程加速倍数是多少？
2. **解释：** 为什么一台电脑还有大量 SSD 空间，却可能因内存压力而卡顿？
3. **迁移：** 相机每秒上传一张小图，云端推理只占总时间的十分之一，应该先测什么？

<details>
<summary>答案要点与常见误区</summary>

1. 总耗时为四十四毫秒，加速约为 2.73 倍；不是上一轮整体速度再翻倍。
2. SSD 与主存承担不同任务，容量不能互相等同；系统可能在频繁搬移当前需要的数据。
3. 先分别测采集、编码、网络、排队、推理和保存的耗时；剩余九成时间决定主要优化空间。

常见误区：GPU 一定比 CPU 快；显存足够就代表系统足够快；单帧延迟等于稳定吞吐量的倒数。
只有在明确的串行处理等假设下，这些指标才可能形成简单对应。

</details>

## 进阶延伸（可选）：以后再追问实现细节

<details>
<summary>工作集、缓存组织与 CUDA 线程块</summary>

**工作集**是程序在一段时间内反复使用的那批数据和指令；它能否放进某层缓存，会影响实际等待。真实机器还可能把取指令的缓存和取数据的缓存分开，这不改变“程序指令也能被存储”的基本思想；见 [MIT 存储层次讲义](https://computationstructures.org/lectures/caches/caches.html)。

**CUDA** 是 NVIDIA 的一套 GPU 编程平台。它把工作描述成许多可分别推进的指令序列，称为线程，再把线程组织成**线程块**，便于安排计算与协作。这里的分组方式不是“一块等于一个物理核心”，也不保证所有分组同时运行；见 [NVIDIA 编程模型](https://docs.nvidia.com/cuda/cuda-programming-guide/01-introduction/programming-model.html)。先理解哪些工作可以同时做，再学这些分组与调度细节。

</details>
