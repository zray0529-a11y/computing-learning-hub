# 09 分布式系统：面对延迟、重复与局部故障

## 核心判断

多台机器合作以后，“部分成功”会成为正常状态。分布式设计首先要回答数据可能晚到、重复到、永远不到时怎么办，再考虑增加节点。

先修：[网络](06-networks.md)、[数据库事务](07-databases.md)、[软件契约](08-software-engineering.md)。

## 为什么远程调用不同于本地函数

本地函数返回异常通常较容易定位到一次执行；远程请求超时则至少有三种可能：请求没有到、服务执行失败、服务已经成功但响应丢失。调用方仅凭超时无法区分。

比如“创建一张工单”的接口超时，立即重试可能创建两张工单。解决方式可以是给这次业务操作一个稳定的幂等键，接收方保存处理结果；同一个键的重复请求返回已有结果，而不是重复执行。

建筑类比是不同施工单位通过邮件交接：邮件未回复不等于现场没做。边界在于计算机系统会高频自动重试，重复和乱序可能远超人工交接规模，不能仅靠“再确认一下”的习惯解决。

| 概念 | 精确定义方向 | 不要误读成 |
|---|---|---|
| Partial failure／局部故障 | 一部分组件失败，其他部分仍运行 | 整个系统必然一起停机 |
| Idempotence／幂等 | 重复同一操作不增加额外业务效果 | 接口永远只被调用一次 |
| Replication／复制 | 多份数据或状态副本 | 备份已验证可恢复 |
| Sharding／分片 | 不同节点负责不同数据子集 | 复制同一份数据 |
| Consensus／共识 | 节点在故障模型下对值或日志达成一致 | 多个LLM投票 |
| Event time／事件时间 | 事情发生或采集的时间 | 消费者读到消息的时间 |
| Backpressure／背压 | 下游处理不及时，向上游反馈限制流量 | 只把队列无限加长 |
| Eventual consistency／最终一致性 | 满足条件且不再更新后副本逐渐收敛 | 不管怎么写最后都会正确 |

## CAP必须带着条件理解

CAP讨论的是特定网络和故障模型中的一致性、可用性与分区。发生网络分区时，若两边不能通信，又要求所有对非故障节点的请求都得到符合定义的响应，就无法同时保证线性一致性。它不是日常架构随意“三选二”的采购清单。

这里的C是可以把操作看作遵循单一实时顺序的强一致性；A也不是“全年99.9%在线”的SLA口径。真实系统需要具体到某个操作、某种故障和可接受的行为。原始证明与定义见[Gilbert与Lynch，2002](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer6.pdf)。

可接受旧状态的地图提示，与要求多个客户端看到同一实时更新顺序的库存操作，可能选择不同策略。防止同一请求重复扣减则属于幂等问题，不能与线性一致性混为一谈。不能给整个产品贴一个“CP”或“AP”标签就代替细节设计。

## 队列、日志和共识各自解决什么

Kafka等事件流系统可以保存并分发事件，让采集与处理解耦；它不会自己判断一帧图像表示什么。[Kafka官方介绍](https://kafka.apache.org/intro/)

同一分区内的日志顺序，不等于跨分区的全局业务时间顺序。消费位点反映处理进度；业务表是否已提交、外部通知是否已发送，还需要事务或幂等协议协调。不要由“消息系统有 exactly-once 功能”推出“任意外部动作恰好发生一次”。

共识用于让多个副本对日志顺序等达成一致。Raft把这件事分解为领导者选举、日志复制和安全性约束等问题；通常需要多数节点可通信才能持续推进。[Raft作者项目页](https://raft.github.io/)

模型投票则是在比较不确定的判断，所有模型可能共享同一个错误来源；它与分布式共识所证明的系统性质不同。

## 最小实验：重复和乱序事件

这里假设单一来源提供可靠、递增的版本号。同一版本出现冲突时应报警或隔离，不能默默覆盖；多来源时需要另外定义冲突规则。

```python
events = [('e2', 2, 'high'), ('e1', 1, 'low'), ('e2', 2, 'high')]
seen = set()
latest = None
for event_id, version, state in events:
    if event_id in seen:
        continue
    seen.add(event_id)
    if latest is None or version > latest[0]:
        latest = (version, state)
print(len(seen), latest)
```

预期：`2 (2, 'high')`。后到的旧事件没有覆盖新状态，重复事件没有增加计数。这段内存代码没有持久性、并发安全或事务保证，只演示规则，不能当作生产消费程序。

## 从数量推导容量，不先猜GPU

以下全部是教学假设，不是项目实测：20,000路相机，每300秒取1帧，均匀到达时平均流量约为66.7帧/秒。如果每帧占用一个处理槽0.8秒，理想平均在途工作量约为53.3个，因此54个槽只是达到平均吞吐的粗下界。

还要考虑突发、慢样本、重试、批处理、解码和数据传输。一个处理槽也不等于一块GPU。实际容量要在指定模型、分辨率、硬件和批量设置下测得。

队列长度上升说明到达与处理不平衡，但根因可能是网络、CPU、数据库或模型。先分段测量吞吐、排队时间和错误，再决定限流、丢弃过期任务、增加并行度或改变采样。

## 闭卷检查

1. 接口超时之后，为什么不能断言“操作没有成功”？
2. 旧观察最后到达，直接按入库顺序更新当前状态会怎样？
3. 两个网络隔离的入口都能修改同一库存，又要求立即成功且强一致，冲突在哪？

<details>
<summary>答案要点与纠错</summary>

1. 服务可能已提交，只是响应丢失；应查询业务结果或使用可靠的幂等机制。
2. 会让旧事实覆盖新事实；必须定义事件时间、版本与冲突处理规则，并区分接收时间。
3. 分区中两边无法确认对方修改，不能同时保证定义下的可用性和线性一致性；要阻塞部分操作或允许某种弱一致及后续处理。

若你只会说“用Kafka就好了”，请补充消费者崩溃时哪些数据已写入、重放后如何去重、外部动作如何避免重复。
