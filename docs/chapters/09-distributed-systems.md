# 09 分布式系统：面对延迟、重复与局部故障

图解里，客户端用 `K1` 请求创建工单，服务已经保存了 **`K1 → 工单7`**，响应却在途中丢失。客户端超时后仍用 `K1` 重试，服务查到记录，返回同一个工单7。先看清“服务已经做完”和“客户端知道结果”是两件事，再讨论多台机器怎样合作。

## 核心判断

多台机器合作以后，“部分成功”会成为正常状态。分布式设计首先要回答数据可能晚到、重复到、永远不到时怎么办，再考虑增加节点。

先修：[网络](06-networks.md)、[数据库事务](07-databases.md)、[软件契约](08-software-engineering.md)。

## 为什么远程调用不同于本地函数

本地函数返回异常通常较容易定位到一次执行，但它也可能已经产生了部分副作用。远程调用又多了通信的不确定性：请求没有到、服务执行失败、服务已经成功但响应丢失，都可能表现为客户端超时。调用方仅凭超时无法区分。

比如“创建一张工单”的接口超时，立即当成新操作重试可能创建两张工单。**幂等（idempotence）** 要求重复同一操作不增加额外的预期业务效果；图里的**幂等键** `K1` 就是给“这一次创建”贴上的稳定身份。接收方保存键与结果，重复收到 `K1` 时返回工单7；换成新键 `K2`，则可能被视为另一笔创建。

这个约定必须落到执行规则：同键但内容不同要识别为冲突；键和业务结果需可靠保存，并处理同时到达的请求、事务范围和记录保留期。先查内存字典再写库，在并发或崩溃下并不自动安全。HTTP 对幂等方法和自动重试也有明确条件，不能因为某个请求失败就任意重发。[RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

重试需要次数与总时间预算。暂时性故障可以延迟后再试，并让不同客户端错开重试时间；永久性的输入错误应先修正输入，无差别重试只会增加负载。

建筑类比是不同施工单位通过邮件交接：邮件未回复不等于现场没做。边界在于计算机系统会高频自动重试，重复和乱序可能远超人工交接规模，不能仅靠“再确认一下”的习惯解决。

| 概念 | 精确定义方向 | 不要误读成 |
|---|---|---|
| Partial failure／局部故障 | 一部分组件失败，其他部分仍运行 | 整个系统必然一起停机 |
| Idempotence／幂等 | 重复同一操作不增加额外业务效果 | 接口永远只被调用一次 |
| Replication／复制 | 多份数据或状态副本 | 备份已验证可恢复 |
| Sharding／分片 | 不同节点负责不同数据子集 | 复制同一份数据 |
| Consensus／共识 | 节点在故障模型下对值或日志达成一致 | 多个LLM投票 |
| Event time／事件时间 | 事情发生或采集的时间 | 消费者读到消息的时间 |
| Backpressure／背压 | 下游处理不及时，向上游反馈限制流量 | 只把队列无限加长 |
| Eventual consistency／最终一致性 | 满足条件且不再更新后副本逐渐收敛 | 不管怎么写最后都会正确 |

## 先看两本不同步的库存簿，再理解 CAP

假设东门和西门都显示只剩 1 个预约名额。两边网络断开，东门刚确认售出，西门却收不到消息。西门若继续把旧库存当成当前值，会违背两边共用一份实时库存的承诺；若必须先等确认，隔离期间就不能保证所有请求都完成。这是多副本之间要明确的取舍。

**网络分区（partition）** 指一组节点与另一组节点无法通信，不要求每台机器都已故障。**CAP** 讨论特定故障模型中的一致性（C）、可用性（A）与分区容忍（P）：发生分区时，如果要求所有到达非故障节点的请求最终得到符合要求的响应，就不能同时保证线性一致性。它不是日常架构随意“三选二”的采购清单。

这里的 **C，线性一致性**，要求操作表现得像对一份副本按单一顺序执行，而且尊重实际先后：一个写入已经完成，之后开始的读取不能假装这次写入尚未发生。它与[数据库章节](07-databases.md)中 ACID 的 C 不同，后者关注事务维护已声明的约束与业务底线。**A** 也不是“全年99.9%在线”的可用率口径；原始定义要求最终响应，并不规定一个固定的响应时限。原始定义与证明见[Gilbert与Lynch，2002，§2–3](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer6.pdf)。

可接受旧状态的地图提示，与要求多个客户端看到同一实时更新顺序的库存操作，可能选择不同策略。防止同一请求重复扣减则属于幂等问题，不能与线性一致性混为一谈。不能给整个产品贴一个“CP”或“AP”标签就代替细节设计。

## 先存下事件，再让不同处理者各自推进

采集速度和识别速度不一致时，不必让每台相机等全部处理完成再继续。可以先把事件记在一份流水台账上，识别、统计等处理者按自己的进度读取。这样让生产事件和处理事件不必同步等待，称为**解耦**。

**Kafka** 是一种保存、分发事件流的系统。它把一类事件放在一个 **topic（主题）** 中；主题可分成几本台账，每本叫 **partition（分区）**，新记录追加到某一分区。这里的“分区”是数据组织方式，与上节“网络分区”含义不同。[Kafka 官方介绍](https://kafka.apache.org/intro/)

每条记录在所属分区中有一个位置编号，叫 **offset（偏移量）**。下面是虚构的局部台账：

| 分区 | offset | 事件 |
|---|---|---|
| P0 | 10 | 东门观察 e10 |
| P0 | 11 | 东门观察 e11 |
| P1 | 10 | 西门观察 w10 |

两个 `10` 在不同台账中，不是同一条记录，也不能比较谁在现实中先发生。同一分区有写入顺序，跨分区没有因此获得统一业务时间顺序。

读取事件的程序叫**消费者**，共同分担一份处理工作的程序组成**消费组**。**消费位点**像消费组在每本台账中保存的书签：识别组与统计组可以各有进度，还要分清“已经取到哪里”和“已经可靠保存的进度”。在这份连续编号的例子中，处理完 P0 的 10 后提交位点 11，表示恢复时从 11 继续。取到一批记录时，读取位置可能已前移，业务处理却还没完成；提交位点不会自动替你提交业务表。[KafkaConsumer：位点与消费组](https://kafka.apache.org/42/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

如果业务表写完、书签还没保存就崩溃，恢复后可能再次处理；如果先保存书签、业务处理随后失败，又可能跳过该做的事。因此业务写入、消费进度和外部通知仍需事务或幂等协议协调。不能由“消息系统支持 exactly-once（限定范围内的恰好一次处理语义）”推出“任意外部动作恰好发生一次”。

**类比边界：** 追加台账不意味着永久保存，系统会按保留或压缩规则清理记录，offset 也不保证留下的记录编号连续。Kafka 不会判断一帧图像的含义，也不会替业务决定不同来源的冲突规则。

## 台账还要保存多份：Raft 怎样协调副本

如果台账只保存在一台机器上，它故障后就无法继续。复制多份以后，又出现“下一条到底记什么”的问题。**共识（consensus）** 是在约定的故障模型下，让副本对要确认的值或日志顺序达成一致；这里的日志是有序的操作记录。

先想象固定的 5 个分部，每个留一份台账。**Raft** 在正常时期由一名 **leader（领导者）** 组织追加记录，其余节点跟随复制；发生故障时重新选举。超过半数在这里是 3 个，包含领导者自己的那一份。任意两个三人多数都会重叠，但正确性还需要所有人遵守同一套选举、持久化和日志规则。[Raft 原论文，§5](https://raft.github.io/raft.pdf)

**term（任期）** 是递增的选举轮次编号。每个节点同一任期最多投一票，候选者还必须通过日志新旧的检查；同一任期最多选出一名领导者。选举中可能同时有多个候选者，网络隔离的旧领导者也可能暂时不知道新任期；“任何时刻全网都知道唯一负责人”并不是协议前提。

领导者把自己当前任期的一条记录按协议可靠复制到至少 3 台（含自己）后，可以确认提交，再让副本按日志顺序执行。这里的“确认”依赖实际存储和回复，发出了三个请求不等于已经满足条件。

在这个固定五节点例子中，只有两台能互通的一侧不能独立提交新的日志。它可能仍保存暂未提交的记录，但不能把“本地已经记下”说成“全组已经确认”。Raft 针对遵守协议的节点发生崩溃、延迟和分区等故障，不是防止任意节点造假的投票机制。

<details>
<summary>进阶边界：为什么“收到多数确认”还不够完整</summary>

日志复制要检查前序记录是否匹配，节点还要按规则持久保存任期、投票和日志。领导者通过副本数量判断提交时，直接适用的是**自己当前任期的记录**；旧任期记录不能仅凭“现在多数节点都有”就这样认定提交，而可随当前任期记录提交被间接确认。见原论文 Figure 2、§5.4。单说“多数签字”遗漏了这些安全条件。

</details>

模型投票则是在比较不确定的判断，所有模型可能共享同一个错误来源；它与分布式共识所证明的系统性质不同。

## 最小实验：重复和乱序事件

这里假设单一来源提供可靠、递增的版本号。同一版本出现冲突时应报警或隔离，不能默默覆盖；多来源时需要另外定义冲突规则。

```python
events = [('e2', 2, 'high'), ('e1', 1, 'low'), ('e2', 2, 'high')]
seen = set()
latest = None
for event_id, version, state in events:
    if event_id in seen:
        continue
    seen.add(event_id)
    if latest is None or version > latest[0]:
        latest = (version, state)
print(len(seen), latest)
```

预期输出：

```text
2 (2, 'high')
```

后到的旧事件没有覆盖新状态，重复事件没有增加计数。这段内存代码没有持久性、并发安全或事务保证，只演示规则，不能当作生产消费程序。

## 从数量推导容量，不先猜GPU

以下全部是教学假设，不是项目实测：20,000路相机，每300秒取1帧，均匀到达时平均流量约为66.7帧/秒。如果每帧占用一个处理槽0.8秒，理想平均在途工作量约为53.3个，因此54个槽只是达到平均吞吐的粗下界。

还要考虑突发、慢样本、重试、批处理、解码和数据传输。一个处理槽也不等于一块GPU。实际容量要在指定模型、分辨率、硬件和批量设置下测得。

队列长度上升说明到达与处理不平衡，但根因可能是网络、CPU、数据库或模型。先分段测量吞吐、排队时间和错误，再决定限流、丢弃过期任务、增加并行度或改变采样。

## 闭卷检查

1. 接口超时之后，为什么不能断言“操作没有成功”？
2. 旧观察最后到达，直接按入库顺序更新当前状态会怎样？
3. 两个网络隔离的入口都能修改同一库存，又要求立即成功且强一致，冲突在哪？
4. 第一次 `K1` 已创建工单7，重试改成 `K2` 会带来什么风险？
5. 已经取到 Kafka 的一批事件，为什么不等于业务表已经写好？
6. 五节点 Raft 中，隔离出来的两台都同意一个新记录，能否独立确认提交？

<details>
<summary>答案要点与纠错</summary>

1. 服务可能已提交，只是响应丢失；应查询业务结果或使用可靠的幂等机制。
2. 会让旧事实覆盖新事实；必须定义事件时间、版本与冲突处理规则，并区分接收时间。
3. 分区中两边无法确认对方修改，不能同时保证定义下的可用性和线性一致性；要阻塞部分操作或允许某种弱一致及后续处理。
4. 新键可能被视为另一笔创建，产生第二张工单；它不会自动撤销第一次的结果。
5. 读取位置、可靠提交的消费进度和业务写入是不同状态；崩溃和重放需要明确协调规则。
6. 不能。两台不是固定五节点配置的多数，而且完整提交还要遵守任期与日志等规则。

若你只会说“用Kafka就好了”，请补充消费者崩溃时哪些数据已写入、重放后如何去重、外部动作如何避免重复。

</details>
