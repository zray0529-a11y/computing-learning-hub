# 07 数据库：把事实、关系与变化保存下来

## 核心判断

数据库的价值是让多个人、多个程序，在持续变化的数据上仍能可靠地查询和更新。学习起点是“什么事实需要保存、什么条件永远不能被破坏”，然后才是选数据库产品。

先修：[数据结构](04-algorithms.md)、[程序与接口](03-programming.md)。本章的相机数据均为教学虚构。

## 先把对象分清楚

假设你要回答“东门现在拥不拥挤”。地点、相机和观察记录是不同对象：地点可以多年不变，相机可能转向，观察每隔几分钟就变化。把它们塞成一条不断覆盖的文字，会丢失历史和证据关系。

一个起步模型可以是：

| 表 | 一行代表什么 | 重要字段 |
|---|---|---|
| entity | 一个有独立身份的地点 | entity_id、name |
| camera | 一个采集设备 | camera_id、source_id |
| observation | 一次有时间的采集或观察来源 | observation_id、camera_id、observed_at、evidence_ref |
| observation_entity | 该次观察对一个实体的判断 | observation_id、entity_id、relation_type、state |

最后一张表处理“一相机可能观察多个实体”。同一帧里的两个入口可能一处拥挤、一处空闲，因此实体状态放在对应的关联记录上，不能把整帧一个状态广播给全部实体。这只是教学建模，不代表现有生产系统的实际表结构。

## 关键概念

| 概念 | 解决的问题 | 容易混淆之处 |
|---|---|---|
| Schema／模式 | 字段、类型、约束和关系怎么定义 | JSON 灵活也仍需要数据契约 |
| Primary key／主键 | 如何唯一指认一行 | 名称可能重名，不适合随意当身份 |
| Foreign key／外键 | 引用的对象是否存在 | 外键存在不代表业务关联正确 |
| Constraint／约束 | 哪些坏数据必须拒绝 | 非空约束不验证内容真实性 |
| JOIN／连接 | 怎样按键组合多个表 | 连接条件错误可能把行数成倍放大 |
| Index／索引 | 怎样缩小查询范围 | 加速部分读取，同时增加空间和写入成本 |
| Transaction／事务 | 多步更新怎样一起成功或回退 | 不自动使外部 API 调用一起回滚 |
| Isolation／隔离 | 并发事务能看见哪些状态 | 不同隔离级别提供不同保证 |

## 从查询理解索引

“查某相机最近十条观察”实际上包含三个要求：限定 camera_id、按 observed_at 排序、限制结果数量。数据库可以扫描全表再过滤排序，也可能使用合适的复合索引缩小工作量。

索引像图纸目录：找图快了，但每次增加或修改图纸，目录也要维护。类比边界是，数据库优化器还会根据数据分布、选择性和代价选择执行计划；“建了索引”不等于“所有查询都使用索引”。应通过真实查询计划和测量判断。[PostgreSQL 索引说明](https://www.postgresql.org/docs/current/indexes.html)

规范化先把不同事实放在各自的位置，避免相机名称更新时需要改动几百万条历史观察。为了读取速度保留一些冗余字段也可能合理，但必须说明权威来源、更新方式和允许的滞后。

## 事务真正保证什么

一次操作可能同时写入观察记录和更新最新状态。如果只完成一半，下游会得到互相矛盾的结果。事务把这些数据库内的步骤绑定成一个提交单位；失败时可以回滚。[PostgreSQL 事务教程](https://www.postgresql.org/docs/current/tutorial-transactions.html)

常见 ACID 四个字母分别指原子性、一致性、隔离性、持久性。这里的一致性主要是让已声明的约束与业务不变量保持成立，不是 CAP 中的线性一致性，也不是“数据一定符合现实”。

例如错误的实体匹配可以完整地提交并持久保存。数据库保证了写入过程，却无法替你证明“这个摄像头确实拍到了东门”。这需要业务校验与证据。

数据库事务也不等于跨系统事务。数据库提交成功、短信接口超时，不能凭一次 ROLLBACK 撤回已经发送的短信。跨系统恢复需要幂等、状态机和补偿，见[分布式系统](09-distributed-systems.md)。

## 最小实验：重复主键触发整体回滚

以下只使用内存数据库和虚构记录。需要带 sqlite3 模块的 Python 3。为突出回滚，实验把一次单实体判断简写成一张表，没有复刻上面的多实体模式。

```python
import sqlite3

db = sqlite3.connect(':memory:')
db.execute('CREATE TABLE observation (id TEXT PRIMARY KEY, state TEXT NOT NULL)')
db.execute('INSERT INTO observation VALUES (?, ?)', ('e1', 'low'))
db.commit()
try:
    with db:
        db.execute('INSERT INTO observation VALUES (?, ?)', ('e2', 'high'))
        db.execute('INSERT INTO observation VALUES (?, ?)', ('e1', 'medium'))
except sqlite3.IntegrityError:
    print('rollback')
print(db.execute('SELECT id, state FROM observation ORDER BY id').fetchall())
db.close()
```

预期输出：先是 `rollback`，再是 `[('e1', 'low')]`。e2 虽先插入，也因同一事务后面的异常而撤销。这里用参数占位传值；不要把外部输入直接拼进 SQL。连接上下文管理器的行为及参数传递见[Python sqlite3 文档](https://docs.python.org/3/library/sqlite3.html)。

变式：把两次插入拆成两个已提交事务，再预测 e2 是否保留。先说理由，再改代码验证。

## 关系、文档、图、向量如何选择

这是根据访问模式提出的设计建议，不是数据库产品排名。

| 主要问题 | 可先考虑 | 仍需解决 |
|---|---|---|
| 按字段过滤、聚合、有明确约束 | 关系表与 SQL | 模式设计、事务边界、索引 |
| 结构随来源变化的嵌套材料 | JSON／文档表示 | 校验、版本兼容、必要字段抽取 |
| 多跳关系与路径 | 图模型 | 关系含义、更新一致性、规模 |
| 空间范围和距离 | 空间索引 | 坐标系、单位、精度 |
| 与一段文本语义相近的材料 | 向量检索 | 召回评估、过滤、权限和证据 |

同一个数据库可能支持其中多个能力。图查询不必自动引入独立图数据库；向量相似不表示两个实体是同一个。先用样本查询验证需求，再决定是否引入新系统。

## 闭卷检查

1. 给相机名称加 UNIQUE，能否保证相机与实体正确匹配？
2. 为什么只保存“最新状态”难以复盘一次错误回答？
3. 写库成功而远程接口超时，直接重跑整段业务有什么风险？

<details>
<summary>答案要点与纠错</summary>

1. 只能限制同一表中相同名称的重复；名称可能不稳定或多个设备共用相近名称，语义匹配还需其他证据。
2. 最新值覆盖了观察时间、过去状态、模型版本和证据来源。历史观察与当前视图应分开考虑。
3. 外部操作可能已经成功。重试前需要业务唯一键、幂等设计或查询实际结果，不能把网络错误直接当作业务未执行。

若你只能背出 ACID，却不能预测实验中的 e2 是否存在，说明还需要操作层面的练习。

</details>
