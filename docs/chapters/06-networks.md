# 06｜网络：让不同机器交换可解释的消息

> **一句话核心：网络协议分层解决寻址、传输、保护与解释消息的问题，业务成功需要端到端确认。**

相机上传数据、浏览器展示城市模型、Agent 调用工具，看起来都是“请求一个接口”。
但请求可能还没到、已经执行却丢了响应，或者成功返回了不符合业务预期的数据。
理解这些不同状态，是设计超时、重试和排查故障的基础。

## 先修与学习目标

先读[程序与接口](03-programming.md)和[操作系统的 I/O](05-operating-systems.md)。
目标是能沿着一次请求指出每层负责什么，以及哪一层的成功不能替另一层作保证。
本章例子都在本地运行，不连接真实相机或服务。

## 关键术语：一条请求经过的约定

- **IP 地址与端口（IP address / port）**：分别帮助定位网络端点与端点上的通信服务。
- **域名系统（DNS）**：查询域名相关记录的系统，常用于取得目标 IP 地址。
- **分组（packet）**：网络中传输和转发的数据单元；大消息通常涉及多个分组。
- **TCP**：提供可靠、有序字节流的传输协议。
- **UDP**：提供数据报传输，不自行保证送达、顺序与去重。
- **HTTP**：定义请求、响应、方法、状态码等应用层语义的协议。
- **TLS**：为通信提供身份认证与加密完整性保护的协议。
- **超时（timeout）**：等待超过预算；它本身不能证明远端没有执行。
- **幂等（idempotency）**：重复相同请求，不增加其预期业务效果。
- **延迟与带宽（latency / bandwidth）**：传输的时间成本与单位时间可传送的数据量。

## 机制一：互联网是网络，Web 是其上的一种应用体系

互联网连接许多网络，利用协议把数据从一个端点送向另一个端点。
Web 使用 URL、HTTP 等机制组织资源访问，浏览器是常见客户端。
电子邮件、远程终端和许多设备通信也使用互联网，但不都属于网页浏览。

分层的意义是让每层只承担一部分责任。
IP 帮助分组跨网络转发；传输层向应用提供通信方式；应用层规定内容的意义。
“已经能访问 IP”不能证明 HTTP 服务正常，“HTTP 正常”也不能证明摄像头画面新鲜。

## 机制二：从域名到应用响应

以访问 `https://example.com/cameras/17` 为例，客户端先解析 URL，明确协议、主机和资源路径。
如果没有可复用结果或连接，通常需要通过 DNS 获得地址，再与目标服务建立通信。
域名与地址并非永久一一对应，同一域名也可以对应多个地址，见 [RFC 1034 §3.6](https://www.rfc-editor.org/rfc/rfc1034.html#section-3.6)。

在典型的新建 HTTP/1.1 或 HTTP/2 的 HTTPS 连接中，客户端建立 TCP 连接，再进行 TLS 协商，随后发送 HTTP 请求。
连接可以复用，因此不是每次请求都必须重做所有步骤。
具体传输路径还取决于 HTTP 版本，不能把此例当成所有网络通信的唯一结构。

请求包含方法、目标、头部及可能的内容；响应包含状态码、头部及可能的内容。
服务器可以返回图像、JSON 或其他表示，HTTP 并不只传 HTML。
这些语义与寻址规则见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。

状态码还要结合接口契约理解：一个成功响应可能只代表接收了任务，后台处理仍未结束。
即使返回了相机状态，也应检查其采集时间、字段和业务状态，而不只看“请求没报错”。

## 机制三：TCP 与 UDP 提供不同的传输承诺

TCP 为字节编号，检测丢失或错误，通过确认与重传等机制恢复有序字节流。
这让应用通常不用自己处理网络分组的乱序和重复。
协议仍可能因连接故障而失败，并不承诺任何网络条件下都能在限定时间送达。
可靠字节流的定义见 [RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)。

“字节流”也意味着 TCP 不替应用保留消息边界。
发送方分两次写入，不代表接收方恰好分两次读到；应用协议要通过长度、分隔符或自身格式识别完整消息。
HTTP 就在传输机制之上定义了自己的消息语义和组织方式。

UDP 保留数据报边界，但不自行保证送达、顺序或避免重复，见 [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html)。
应用可以在它之上加入可靠性机制；实时系统也可以根据用途接受部分丢失。
不能只用“快、慢”比较两者，还要问需要什么语义、丢失时如何处理、拥塞如何控制。

## 机制四：TLS 保护通信，不替你证明业务事实

TLS 通过握手协商密钥等参数，并使用记录协议保护后续通信。
常见 HTTPS 场景会验证服务器证书与目标名称，让客户端确认正在与预期服务通信。
协议目标包括防止窃听、篡改与伪造，见 [RFC 8446 §1](https://www.rfc-editor.org/rfc/rfc8446.html)。

但加密的相机状态仍可能过时，已认证的服务也仍可能返回业务错误。
传输保护不会自动完成用户授权、数据质量检查或业务事务。
把这些责任分开，才能知道应该补哪一种校验。

## 机制五：超时留下不确定性，重试需要业务语义

设想服务器已经保存了一条识别事件，却在返回响应时连接断开。
客户端只看到超时，无法仅凭这个现象区分“请求没到”与“已经保存”。
如果它重新发送创建操作，服务器可能保存第二条事件。

TCP 能处理连接中的字节传输，并不知道两次请求是不是同一个业务动作。
因此，传输可靠不等于业务只执行一次。
HTTP 对幂等方法及自动重试的限制有专门定义，见 [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

一种设计是为同一业务事件分配稳定的请求标识，服务端记住标识及处理结果，重试沿用该标识。
同标识但内容不同应被识别为冲突，而不是悄悄覆盖。
实际系统还要处理并发、记录持久化和保留期限；“在内存字典里查一下”只展示基本思想。

重试也需要次数与时间预算；暂时性故障可以延迟后再试，并让不同客户端错开重试时间。
永久性的输入错误则应先修正输入；无差别重试只会增加负载。
这些选择取决于接口契约和具体故障，而不是统一的“失败就再发”。

## 机制六：高带宽不等于低延迟

假设上传八 MB 数据，按十进制单位换算就是六十四 Mbit。
若可用吞吐量稳定为二十 Mbit/s，光是发送这些数据就约需三点二秒。
DNS、连接建立、排队、传播和服务端处理还可能增加耗时。

对于很小的请求，往返延迟和处理时间可能更显著；增加带宽不一定能明显缩短等待。
而大视频传输更容易受到吞吐与拥塞约束。
因此，应分别测连接、首字节、完整响应和业务完成时间。

## 建筑类比：物流送达与工程验收

运输系统能确认材料包裹送达，但项目仍需检查型号、数量和安装要求。
TCP 更接近可靠运输，应用协议和业务校验更接近交接与验收。
**类比边界：**数字消息可以被复制和重发，确认消息本身也可能丢失，因此“送到过”不等于双方都知道结果。

## 最小实验：重试沿用同一标识

这里手工模拟第一次响应丢失后的第二次提交，不创建网络连接。

```python
ledger = {}
def accept(request_id, payload):
    if request_id in ledger:
        if ledger[request_id] != payload:
            raise ValueError("同一请求标识对应不同内容")
    else:
        ledger[request_id] = payload
    return len(ledger)

print(f"传输估算：{8 * 8 / 20:.2f} 秒")
print("首次记录数：", accept("cam-01:frame-100", "vehicle"))
print("重试记录数：", accept("cam-01:frame-100", "vehicle"))
```

预期输出：

```text
传输估算：3.20 秒
首次记录数： 1
重试记录数： 1
```

如果重试换成新标识，记录数会增加；所以标识代表同一业务事件，而不是每次网络尝试。
本例只保证单进程、顺序执行且记录仍在内存时的行为，不是完整的生产去重实现。

## 闭卷检查：先预测，再解释

1. **预测：**重试时把标识改成 `cam-01:frame-101`，记录数是多少？为什么？
2. **解释：**为什么 TCP 传输成功和收到 HTTP 响应，仍不等于“相机告警已正确处理”？
3. **迁移：**小请求耗时两秒，实际数据发送只占十毫秒，把带宽翻倍大约能改善哪部分？

<details>
<summary>答案要点与常见误区</summary>

1. 记录数变成二；服务端按契约把新标识看作另一个事件，无法自动知道这是错误重试。
2. 前者关注字节流，后者关注协议交换；还需确认业务状态、数据时效以及处理是否已经完成。
3. 在其他条件不变的简化假设下，发送部分约从十毫秒降到五毫秒；其余等待仍需分别调查。

常见误区：互联网等于 Web；域名永远对应一台机器；TCP 自动保留消息边界。
还要避免把超时当作确定失败，把 TLS 当作数据正确性保证，或把每次重试都生成新标识。

</details>
