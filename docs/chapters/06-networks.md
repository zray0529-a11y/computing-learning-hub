# 06｜网络：让不同机器交换可解释的消息

在图解中，你输入虚构网址 `https://learn.example/rooms`，浏览器依次解决四个问题：**DNS 找到地址 → TCP 传递有序字节 → TLS 保护通信 → HTTP 请求 `/rooms` 并解释响应**。本章沿着这一次访问走，不需要真的联网访问这个教学域名。

> **一句话核心：网络协议分层解决寻址、传输、保护与解释消息的问题，业务成功需要端到端确认。**

相机上传数据、浏览器展示城市模型、Agent 调用工具，看起来都是“请求一个接口”。只有把找到谁、怎样传、是否受保护、内容是什么意思分开，才知道出问题时该检查哪里。

## 先修与学习目标

先读[程序与接口](03-programming.md)和[操作系统的 I/O](05-operating-systems.md)。
目标是能沿着一次请求指出每层负责什么，以及哪一层的成功不能替另一层作保证。
本章例子都在本地运行，不连接真实相机或服务。

## 机制一：互联网是网络，Web 是其上的一种应用体系

互联网连接许多网络，利用协议把数据从一个端点送向另一个端点。
Web 使用 URL、HTTP 等机制组织资源访问，浏览器是常见客户端。
电子邮件、远程终端和许多设备通信也使用互联网，但不都属于网页浏览。

大消息通常要拆成网络中传送的数据单元，称为**分组（packet）**。**IP 地址**帮助定位网络端点，**端口**帮助区分端点上的通信服务，可以先类比为建筑地址和收件窗口；它们不是人的真实身份，也不保证永远不变。

分层的意义是让每层只承担一部分责任。IP 帮助分组跨网络转发；传输层向应用提供通信方式；应用层规定内容的意义。
“已经能访问 IP”不能证明 HTTP 服务正常，“HTTP 正常”也不能证明摄像头画面新鲜。

## 机制二：从域名到应用响应

网址又叫 **URL**，它把访问方式、主机名称和资源位置写在一起。例子里，`https` 指出采用受保护的 HTTP 通信，`learn.example` 是主机名，`/rooms` 是资源路径。`rooms` 在这里代表虚构的房间列表。

下面按**没有可用缓存或已有连接、需要新建 HTTP/1.1 或 HTTP/2 的 HTTPS 连接**这一情形说明四层职责。

| 图中的一步 | 先建立直觉 | 实际解决什么 | 还没有保证什么 |
|---|---|---|---|
| DNS：查地址 | 查通讯录，找到收件地址 | 域名系统查询 `learn.example` 的相关记录，常用于取得 IP 地址 | 地址能找到，不代表目标服务可用 |
| TCP：建连接 | 双方给连续运送的内容编号、确认缺失部分 | 提供可靠、有序的字节流，让应用读取按序排列的字节 | 不认识 `/rooms`，也不保证每次读取是一整条消息 |
| TLS：保护通信 | 核对收件方身份，再使用受保护的通信封套 | 协商密钥，验证服务器身份，保护内容的机密性与完整性 | 不判断房间资料是否真实、是否最新 |
| HTTP：请求与响应 | 按统一格式填写申请与回执 | 发送 `GET /rooms` 的请求，接收状态码、头部和可能的正文 | 协议成功不等于所有业务目标已满足 |

DNS 不是“一本永远不变的一对一通讯录”：同一域名可以有多个地址，解析结果也可能在有效期内被缓存。见 [RFC 1034 §3.6](https://www.rfc-editor.org/rfc/rfc1034.html#section-3.6)。TCP 连接是双方维护通信状态的逻辑连接，**不为你铺设或预留一条独占线路**。

已有的 DNS 结果、连接或 HTTP 缓存可能省去部分步骤；因此图解不是每次访问都重复发生的四次独立动作。**HTTP/3 使用基于 UDP 的 QUIC，并把 TLS 安全握手整合进连接建立过程，不经过这里的 TCP 步骤。** 见 [RFC 9114 §2–3](https://www.rfc-editor.org/rfc/rfc9114.html#section-2)。

请求包含方法、目标、头部及可能的内容；响应包含状态码、头部及可能的内容。
服务器可以返回图像、JSON 或其他表示，HTTP 并不只传 HTML。
这些语义与寻址规则见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html)。

状态码还要结合接口契约理解：例如 `202 Accepted` 只表示已接受处理，任务还未完成；`200 OK` 也要按请求方法和接口约定解释。
即使返回了相机状态，也应检查其采集时间、字段和业务状态，而不只看“请求没报错”。

## 机制三：TCP 与 UDP 提供不同的传输承诺

TCP 为字节编号，检测丢失或错误，通过确认与重传等机制恢复有序字节流。
这让应用通常不用自己处理网络分组的乱序和重复。
协议仍可能因连接故障而失败，并不承诺任何网络条件下都能在限定时间送达。
可靠字节流的定义见 [RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)。

为什么要特别强调“字节流”？假设发送方先写入 `ABC`，再写入 `DEF`，接收方可能先读到 `AB`，再读到 `CDEF`，也可能一次读到 `ABCDEF`。顺序相同，**每次读写的边界不一定相同**。见 [RFC 9293 §3.7](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.7)。

可以把它想成连续流过的水：接水时舀了几勺，不能告诉你上游原本倒了几桶。应用必须约定自己的“桶界”，例如长度或分隔符。**类比边界：** TCP 保留的是有序字节，不是混合后无法区分的水，也不会预留一根专用物理管道。

HTTP/1.1 的一类常见响应使用 `Content-Length`（正文的字节数）划定正文边界，头部与正文之间有一个空行；接收方需按协议判断消息是否完整。它也有其他定界规则，不能把这一种格式当作所有 HTTP 的统一解析器。见 [RFC 9112 §2.1、§6.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)。

**UDP** 提供一份一份的**数据报（有边界的传输消息）**，像分开封好的包裹；它保留数据报边界，但不自行保证送达、顺序或避免重复，见 [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html)。
应用可以在它之上加入可靠性机制；实时系统也可以根据用途接受部分丢失。
不能只用“快、慢”比较两者，还要问需要什么语义、丢失时如何处理、拥塞如何控制。

## 机制四：TLS 保护通信，不替你证明业务事实

TLS 通过握手协商密钥等参数，并使用记录协议保护后续通信。
常见 HTTPS 场景会验证服务器证书与目标名称，让客户端确认正在与预期服务通信。
协议目标包括防止窃听、篡改与伪造，见 [RFC 8446 §1](https://www.rfc-editor.org/rfc/rfc8446.html)。

但加密的相机状态仍可能过时，已认证的服务也仍可能返回业务错误。
传输保护不会自动完成用户授权、数据质量检查或业务事务。
把这些责任分开，才能知道应该补哪一种校验。

## 机制五：高带宽不等于低延迟

**延迟**是一次传输或交互付出的时间，**带宽**描述单位时间可传送的数据量；实际传送速度还受共享资源和协议影响，通常用测得的**吞吐量**表示。把运输车道加宽，不会让每辆车瞬间到达。

假设上传八 MB 数据，按十进制单位换算就是六十四 Mbit。
若可用吞吐量稳定为二十 Mbit/s，光是发送这些数据就约需三点二秒。
DNS、连接建立、排队、传播和服务端处理还可能增加耗时。

对于很小的请求，往返延迟和处理时间可能更显著；增加带宽不一定能明显缩短等待。
而大视频传输更容易受到吞吐与拥塞约束。
因此，应分别测连接、首字节、完整响应和业务完成时间。

若等待超过预算，就发生了**超时**。超时只说明没有按时得到结果，不能证明远端没有执行；“已执行但响应丢失”以及如何避免重复创建，留到[分布式系统](09-distributed-systems.md)用 `K1 → 工单7` 的完整例子讨论。

## 建筑类比：物流送达与工程验收

运输系统能确认材料包裹送达，但项目仍需检查型号、数量和安装要求。
TCP 更接近可靠运输，应用协议和业务校验更接近交接与验收。
**类比边界：** 数字消息可以被复制和重发，确认消息本身也可能丢失，因此“送到过”不等于双方都知道结果。

## 最小实验：三块字节不等于三条消息

假设 `/rooms` 返回正文“房间A”。按 UTF-8 编码，它有 7 个字节，而不是 3 个字节：两个汉字各占 3 字节，`A` 占 1 字节。下面把一条 HTTP/1.1 响应手工拆成三块，第二块只带正文的前 2 个字节；先按空行找到头部边界，再按 `Content-Length` 判断正文是否收齐，最后解码成文字。

`b'...'` 表示字节，`encode` 把文字编码成字节，`decode` 再把完整字节解码成文字。`\r\n` 是这里一行的结束符，连续两组标出头部后的空行。本例只模拟固定响应的读取方式，使用 Python 标准功能，不建立网络连接。

```python
body = '房间A'.encode('utf-8')
header = (
    'HTTP/1.1 200 OK\r\n'
    'Content-Type: text/plain; charset=utf-8\r\n'
    f'Content-Length: {len(body)}\r\n\r\n'
).encode('ascii')

# 模拟三次读取：头部也可能被拆开，汉字也可能被拆开
chunks = [header[:17], header[17:] + body[:2], body[2:]]
buffer = b''.join(chunks[:2])
head, partial_body = buffer.split(b'\r\n\r\n', 1)
length = int(head.split(b'Content-Length: ', 1)[1])
print('正文规定字节数：', length)
print('前两块正文完整：', len(partial_body) == length)

buffer += chunks[2]
_, received_body = buffer.split(b'\r\n\r\n', 1)
print('三块后正文完整：', len(received_body) == length)
print('正文：', received_body.decode('utf-8'))
```

预期输出：

```text
正文规定字节数： 7
前两块正文完整： False
三块后正文完整： True
正文： 房间A
```

保持前两块已包含完整头部，再改变正文的切分位置；只要字节没有缺失且顺序不变，最终正文应相同。原例第二块末尾还不足以组成第一个汉字，不能把每次读到的片段都直接当作完整文字。若连头部也尚未收齐，真实程序应继续缓冲，不能急着执行本例的头部解析。

**实验边界：** 这里只有一条已知格式、具有合法 `Content-Length`、没有 `Transfer-Encoding` 的完整响应。真实解析器还必须处理多条消息、大小限制、无正文响应、分块编码、错误与提前断开等情况；HTTP/2 和 HTTP/3 的传输格式也不同。不要把这个教学解析片段直接接到公开服务上。

## 闭卷检查：先预测，再解释

1. **预测：** 发送方写入两次，接收方读到三块，能否判断产生了三条 HTTP 消息？为什么？
2. **解释：** 为什么 TCP 传输成功和收到 HTTP 响应，仍不等于“相机告警已正确处理”？
3. **迁移：** 小请求耗时两秒，实际数据发送只占十毫秒，把带宽翻倍大约能改善哪部分？
4. **定位：** 能解析 `learn.example` 的地址，但服务器证书验证失败，四步里卡在哪里？

<details>
<summary>答案要点与常见误区</summary>

1. 不能。读取块边界不是应用消息边界；实验的三块共同组成一条响应，需按 HTTP 格式解析。
2. 前者关注字节流，后者关注协议交换；还需确认业务状态、数据时效以及处理是否已经完成。
3. 在其他条件不变的简化假设下，发送部分约从十毫秒降到五毫秒；其余等待仍需分别调查。
4. TLS 身份验证阶段。DNS 成功并没有证明通信对象已通过认证，也没有证明 HTTP 请求成功。

常见误区：互联网等于 Web；域名永远对应一台机器；TCP 自动保留消息边界。
还要避免把 TCP 连接想成独占线路，把超时当作确定失败，或把 TLS 当作数据正确性保证。

</details>
