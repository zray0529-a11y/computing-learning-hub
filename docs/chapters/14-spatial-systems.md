# 14 空间与数字孪生：连接位置、外观、语义和实时状态

## 核心判断

位置、三维外观、实体身份与实时状态是四类不同信息。把场景渲染得逼真，不会自动得到正确的语义、可行走路线、当前人流或物理仿真。

先修：[图与算法](04-algorithms.md)、[数据库](07-databases.md)、[数学与ML](10-math-and-ml.md)。本章通过通用的城市、建筑与景区场景，练习基础知识在空间系统中的应用。

## 把系统拆成能分别验证的层

| 层 | 主要问题 | 典型数据与检查 |
|---|---|---|
| 空间参考 | 对象到底在哪里 | 坐标系、单位、控制点误差 |
| 几何与外观 | 对象长什么样 | 网格、纹理、影像、点云、Gaussian |
| 实体与关系 | 对象是谁、与谁有关 | 稳定ID、入口关系、道路拓扑 |
| 时间与状态 | 何时观察到什么 | 采集时间、有效期、来源和证据 |
| 交互与决策 | 用户需要怎样的回答或动作 | 查询条件、权限、可解释结果 |

以景区入口为例：模型里有一个门洞，不等于系统已经知道它是可开放的入口；知道名称，不等于知道今天开放；有三分钟前的观察，也不等于知道下一小时的排队时间。

## 坐标先问四件事

坐标属于哪个参考系？各轴如何定义？单位是什么？高度参照是什么？这些没有说明时，两组看起来相近的数不能直接拼接。

GeoJSON标准使用WGS84地理坐标和十进制度；位置的前两个元素是经度、纬度。投影坐标或建筑局部坐标可能以米为单位，转换需要明确映射。[RFC 7946](https://www.rfc-editor.org/rfc/rfc7946)

“两个点差0.001”不是一个完整的距离结论。若是度，距离还与位置、方向和测量模型有关；若是米，则含义完全不同。PostGIS的ST_DWithin在geometry类型中按坐标参考系单位解释距离，在geography类型中用米。[官方定义](https://postgis.net/docs/ST_DWithin.html)

建筑类比是总图坐标与单体局部坐标：每张图单独正确仍可能套合失败。边界是地球曲率、投影、不同高度基准及传感器标定会引入额外误差，不能只靠平移视觉对齐。

## 空间关系与图关系

空间索引可快速找附近候选，但“距离近”不代表“归属于”。同一位置可能有多楼层、多个商铺、不同出入口。实体去重需要身份线索和匹配规则，不能只比较名称或坐标。

图中的节点和边表达关系：入口连接哪条路、路径是否可通行、观察支持哪个实体。父子包含关系、道路连通关系、相机观察关系应明确区分，不能混成一条没有语义的“相关”。

路线搜索需要可通行的拓扑和代价；欧氏距离最近不一定步行最快，隔着围墙、水体或楼层时尤其如此。代价还可能随封闭、坡度、拥挤和无障碍需求变化。

## 最小演算：局部米制坐标的距离

```python
from math import hypot

user = (0, 0)
gates = {'east': (3, 4), 'west': (0, 8)}
distances = {name: hypot(x-user[0], y-user[1]) for name, (x, y) in gates.items()}
print(distances)
print(min(distances, key=distances.get))
```

预期距离为east=5.0、west=8.0，最近的是east。假如东门被围墙隔开，这段代码仍会选它，因为代码没有道路图和通行状态。它只证明一个几何计算，不证明推荐可行。

## 网格、点云、影像与3DGS各能表达什么

网格显式表达表面几何；点云提供离散空间采样；影像主要记录某个视角的外观；3D Gaussian Splatting用带位置、形状和外观参数的高斯表示来重建与渲染视图。原始3DGS工作以多视图图像，以及通过运动恢复结构（SfM）等步骤估计的相机参数和稀疏三维点为起点。[作者项目页](https://repo-sam.inria.fr/fungraph/3d-gaussian-splatting/)

据此做工程推论：逼真渲染质量与测量精度、碰撞体、语义对象、可导航性需要分别验收。一个3DGS场景不会自动提供“哪扇门可进入”的结构；这类能力要另外建立或验证。

单张俯视影像通常不足以唯一确定遮挡立面和背面的真实几何。生成式补全可以形成视觉假设，但不能当作已采集的现场证据。这是观测信息不足的约束，不是换一个渲染引擎就能消除。

大范围场景常通过分块和不同细节层级控制加载与渲染成本。数据传输、解码、内存和GPU绘制都可能成为瓶颈；性能必须说明设备、分辨率、视角与数据规模，不能照搬论文帧率。

## 静态底图与实时证据怎样连接

稳定的entity_id连接实体资料；观察记录追加保存observed_at、received_at、state、source_id和evidence_id。当前状态是根据这些记录及有效期规则计算出的视图。

如果相机转向，旧观察关系未必继续成立；如果某个入口没有可用观察，不能把另一处的状态自动搬过来。来源之间冲突时，应保留分歧与时间，不把模型的自然语言总结作为新的权威事实。

一次C端回答可以分为：观察到的状态及时间、证据覆盖范围、基于状态的建议、仍待用户选择的因素。这个结构便于区分事实、推断与偏好。

## 闭卷检查

1. 一个看起来非常真实的景区3D模型，为什么仍可能无法导航？
2. 相机A能看见两个入口，数据库关系应该怎么表达？
3. 为什么“距离最近”和“当前最快到达”需要不同数据？

<details>
<summary>答案要点与纠错</summary>

1. 可能没有可通行道路拓扑、入口语义、尺度标定或碰撞结构；外观只覆盖一类能力。
2. 通过有明确语义的观察关系关联多个实体，并记录关系的有效性与覆盖条件；不能把相机与实体强制一对一。
3. 最近距离只用空间坐标，最快路线还依赖网络拓扑、入口开放、代价和可能的实时状态。
