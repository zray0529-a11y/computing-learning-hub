# 05｜操作系统：让程序安全地共享机器

图解里的单核时间线按 **A、B、A、C** 交替推进。A 等待读取时，B 可以使用处理器；读取完成只是让 A 回到“就绪”，还要等调度才能继续。看起来几个任务都在进行，不代表它们在这个核心上同时计算。

> **一句话核心：操作系统把有限硬件组织成可共享、可隔离、可使用的资源。**

同一台设备要采集视频、运行检测、保存文件并响应界面。这些程序不能随意覆盖彼此内存，也不能都假定自己独占处理器。操作系统安排这些资源，并提供程序能够使用的接口。

## 先修与学习目标

先读[硬件](02-hardware.md)与[编程](03-programming.md)，理解处理器、内存和运行状态。
目标是能区分“程序正在计算”“程序可以运行但还没轮到”“程序正在等待外部事件”。
同时能解释：有多个线程，不等于多个任务在物理上同时计算。

## 机制一：进程像工作室，线程像里面的设计师

如果两个项目都在改图，最先要解决的是“各自的图纸放在哪里，谁能动它”。可以先把一个**进程（process）**想成一间有边界的项目工作室：有自己的图纸桌和进度。同一个程序像同一本工作规程，可以启动多间工作室，各自做到不同的位置。

准确地说，程序是磁盘上的代码等内容，进程是它的一次运行实例。系统为这个实例准备代码、数据和可访问的内存地址范围，记录它执行到哪里。这个地址范围叫**地址空间**，不是进程独占了整台机器的实际内存。
参见 [OSTEP：The Process](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf)。

工作室里可以有几个设计师分工。**线程（thread）**对应进程内部的一条执行路径：一个线程读取视频，一个分析帧，一个提交结果。同一进程中的线程通常共用地址空间，像共用图纸桌，交换数据方便，也容易改到对方正在用的内容。

每个线程仍有自己的执行位置和**栈（保存函数调用等临时状态的工作区）**；共用图纸不等于所有人只有一份工作进度。独立进程交换数据则通常要使用系统提供的通道，例如传送字节的管道、消息，或明确设置的共享内存。
线程模型见 [OSTEP：Concurrency](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-intro.pdf)。

**类比边界：**工作室不是完全独立的机器。进程仍竞争处理器、内存容量和磁盘；线程也不一定能同时使用处理器。隔离与执行速度是两个问题。

## 机制二：调度把并发变成具体的执行顺序

同一台绘图设备不能同时交给所有设计师，操作系统也要决定下一刻让谁使用处理器。这个选择叫**调度（scheduling）**。

在单个处理核心上，多个任务可以交替推进，形成**并发**。
在多核心上，部分任务可能真正同时执行，形成**并行**。
是否并行还受运行时、任务依赖和资源竞争约束，创建线程本身不能保证加速。

与存储、网络、设备等交换数据叫**输入输出（I/O）**。当线程发起需要等待的读取，它可能进入阻塞状态。

| 图中的状态 | 人话解释 | 下一步怎样发生 |
|---|---|---|
| 就绪 | 已经能做，只是还没轮到 | 调度选中后进入运行 |
| 运行 | 正在使用处理器 | 时间片结束可回就绪；等待读取可转阻塞 |
| 阻塞 | 还缺继续执行所需的数据或事件 | 等待结束后回就绪，再由调度选择 |

操作系统可以在 A 阻塞时让 B 运行；A 读取完成后，重新具备运行条件，仍要等调度。
所以“CPU 不忙”不一定表示系统没有工作，也可能表示关键任务正在等数据。

系统可以在适当时机暂停任务，保存执行位置和**寄存器（处理器正在使用的小存储位置）**里的值，再恢复另一任务。这个保存与恢复过程叫**上下文切换**，像先夹好书签再换一份工作。
调度策略在响应速度、公平与吞吐之间做选择，切换本身也有成本。
线程数量远多于实际可用资源时，更多切换与竞争可能抵消收益。

## 机制三：虚拟内存首先是一种地址抽象

两个工作室都说“第一号图纸柜”，未必指向同一个柜子。类似地，两个进程都可以使用相同的虚拟地址，却对应不同的物理位置。**虚拟内存**把程序看到的地址与实际物理存储安排分开；操作系统与硬件合作完成映射和权限检查，让程序不必直接管理整台机器的物理布局。
地址抽象与隔离目标见 [OSTEP：Address Spaces](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-intro.pdf)。

因此，“虚拟内存”不等于“把硬盘当内存”。
利用持久存储暂存部分内存内容，只是某些内存管理机制的一部分。
即使没有把内存内容暂存到磁盘，地址映射与进程间隔离仍然有意义。

隔离也有明确范围：线程共享同一进程地址空间时，一个线程错误修改对象，其他线程可能同时受到影响。
而进程隔离也不能消除 CPU、内存容量和磁盘等共享资源上的竞争。
需要根据故障边界和数据交换成本选择结构。

## 机制四：文件和 I/O 把设备细节收在接口后面

应用可以请求打开文件、读取字节和关闭资源，而不必直接控制 SSD 的内部操作。
文件系统管理名称、目录、内容位置和相关元数据；应用仍要负责解释文件中的格式。
对文件系统来说，一段坐标表和一张图像首先都可以是字节序列。
参见 [OSTEP：Files and Directories](https://pages.cs.wisc.edu/~remzi/OSTEP/file-intro.pdf)。

这些受保护的资源操作由**内核（操作系统负责资源管理的核心部分）**协调。应用通过**系统调用（向内核提出服务请求的受控入口）**请求读写，不能直接绕过检查随意操作设备。
读写接口可能让调用者等待，也可能提供**异步方式（先继续做别的事，稍后获知完成）**；改变等待方式不会让存储介质瞬间变快。
若生产图像的速度长期大于写盘速度，队列最终仍会增长。

还要区分“写入调用返回”与“数据已经持久保存”。
系统可能先把数据缓存在内存中，再写入设备；需要持久性时，还涉及刷新、文件系统与设备保证。
OSTEP 的文件章节专门讨论 `fsync`，并说明文件内容与目录项都可能需要考虑。

## 机制五：共享数据为什么会丢更新

工作室的两个人共用一份余票表，只剩 1 张票。如果“检查还有票”和“登记售出”分开执行，就可能出现下面三步：

1. A 读到库存 1，认为可以出票。
2. B 也读到库存 1，认为可以出票。
3. A、B 各出一张票，再各自按旧值写回 `1 - 1 = 0`。账面库存是 0，实际上已经卖出 2 张。

问题不一定表现为负库存；旧值覆盖也会掩盖卖超。我们需要让“检查、扣减、登记”作为一整段执行，相对于其他参与者不被中途穿插，这就是这里要的**原子性**。

假设计数初始为零，两个线程都要执行“读取、加一、写回”。
若两个线程先后都读到零，然后各自写入一，最终结果就是一，而不是二。
问题在于整个复合操作被穿插；源代码只有一行，也不自动获得所需的原子性。

**互斥锁（mutex）**像共用台账的唯一钥匙：把整个检查和更新过程放进受保护的代码区，这块区域叫**临界区**。持锁者操作时，其他遵守同一把锁的线程必须等待。
只锁住最后的写回，仍可能保留前面“都读到旧值”的问题。
锁的正确使用还要求共享数据的所有相关访问都遵守相同协议。

锁也会引入等待：若任务甲持有锁 A 等锁 B，任务乙持有锁 B 等锁 A，就可能互相等下去，这叫**死锁**。
固定获取顺序、减少持锁范围、采用明确的消息传递方式，都是可分析的设计选择。
这里的互斥不等于崩溃后的持久性，也不能直接替代数据库事务。

## 建筑类比：共享现场与资源预约

进程像有边界的项目工作室，线程像室内共用图纸桌的设计师，调度像安排有限设备的使用顺序。
多人修改同一份设备台账，需要约定谁在什么时候可以更新，就像临界区。
**类比边界：**程序的交错可能发生得极细，不能凭“大家大概不会同时做”保证正确；机器需要明确协议。

## 最小实验：固定顺序看见卖超

先预测：只剩 1 张票，两个人都先读到 1，最终会卖几张，账面还剩几张？下面手工固定这个交错顺序，再对照“一个人完整处理后，另一个人才检查”的顺序。不启动真实线程，所以每次运行都能看到同一个问题。

```python
stock = 1
read_a = stock  # A 先记下旧库存
read_b = stock  # B 也在扣减之前读到同一个旧库存
sold = []
for buyer, old_stock in [('A', read_a), ('B', read_b)]:
    if old_stock > 0:
        stock = old_stock - 1
        sold.append(buyer)
print('交错出票：', len(sold), '库存：', stock)

stock = 1
sold = []
for buyer in ['A', 'B']:
    # 模拟整个临界区依次执行：检查、扣减、登记不能被穿插
    if stock > 0:
        stock -= 1
        sold.append(buyer)
print('整段串行：', len(sold), '库存：', stock)
```

预期输出：

```text
交错出票： 2 库存： 0
整段串行： 1 库存： 0
```

两个结果的库存都为 0，单查库存发现不了重复出票。后半段展示的是正确的串行顺序；真实并发程序还需要用锁等机制保证它，而且所有相关访问必须遵守同一协议。本例不验证某个运行时的线程调度、锁实现或并行速度。

## 闭卷检查：先预测，再解释

1. **预测：**两个线程都读到十，各自加一并写回，按上述交错顺序最后是多少？
2. **解释：**一个程序卡住但 CPU 使用率很低，为什么不能直接判断“处理器太弱”？
3. **迁移：**若视频采集速度持续高于分析速度，单纯不断新增线程能解决什么，又留下什么？
4. **核对：**实验两次最后都剩 0 张票，为什么只有一次结果正确？

<details>
<summary>答案要点与常见误区</summary>

1. 最后是十一，发生了一次更新覆盖；正确累计应是十二。
2. 程序可能在等网络、存储、锁或其他任务，应先观察等待原因和资源路径。
3. 若尚有可用资源，并发可能改善吞吐；若已经达到瓶颈，仍需限制队列、降低输入、丢弃可丢帧或增加有效处理能力。
4. 还要检查售出数量。第一段把一张票卖给了两人，旧值写回掩盖了卖超；第二段 B 检查时已看到库存 0。

常见误区：线程越多越快；共享地址空间代表没有独立状态；虚拟内存只是交换文件。
另一个误区是“写成功就一定抗断电”，以及“某次并发测试没错就证明没有竞争”。

</details>
