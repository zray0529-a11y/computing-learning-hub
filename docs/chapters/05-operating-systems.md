# 05｜操作系统：让程序安全地共享机器

> **一句话核心：操作系统把有限硬件组织成可共享、可隔离、可使用的资源。**

同一台设备可以同时采集视频、运行检测、保存文件并响应界面。
这些程序不能随意覆盖彼此内存，也不能都假定自己独占处理器。
操作系统提供执行、内存与文件等抽象，并安排底层资源，让这种共存成为可能。

## 先修与学习目标

先读[硬件](02-hardware.md)与[编程](03-programming.md)，理解处理器、内存和运行状态。
目标是能区分“程序正在计算”“程序可以运行但还没轮到”“程序正在等待外部事件”。
同时能解释：有多个线程，不等于多个任务在物理上同时计算。

## 关键术语：从运行实例到共享资源

- **进程（process）**：程序的一次运行实例，带有地址空间、执行状态和资源。
- **线程（thread）**：进程中的执行路径；同一进程的线程通常共享地址空间。
- **内核（kernel）**：操作系统中负责资源管理和受保护操作的核心部分。
- **系统调用（system call）**：应用请求内核服务的受控入口。
- **调度（scheduling）**：从可运行任务中选择由谁使用处理器。
- **上下文切换（context switch）**：保存当前执行状态并恢复另一任务状态。
- **虚拟内存（virtual memory）**：把程序看到的地址与实际物理存储安排分开。
- **输入输出（I/O）**：与存储、网络、设备等交换数据。
- **互斥锁（mutex）**：约束同一时刻进入受保护区域的执行者。
- **原子性（atomicity）**：对所讨论的观察者而言，一组操作不可被中途穿插。

## 机制一：程序是规则，进程是一次正在发生的执行

源文件或可执行文件放在磁盘上时，只是一组内容。
启动后，系统为运行实例准备执行环境，装入需要的代码与数据，并记录当前执行位置。
同一个程序可以启动多个进程，它们的运行状态不必相同。
参见 [OSTEP：The Process](https://pages.cs.wisc.edu/~remzi/OSTEP/cpu-intro.pdf)。

进程提供资源与隔离边界，线程则提供进程内部的多条执行路径。
例如，一个采集进程中可以有线程读取视频、线程分析帧、线程提交结果。
这些线程能够访问同一批数据，因此交换方便，也因此可能互相干扰。

每个线程有自己的执行位置和栈等状态；“共享地址空间”不表示所有局部状态都合成一份。
相反，独立进程通常需要通过管道、消息或显式共享内存交换数据。
线程模型见 [OSTEP：Concurrency](https://pages.cs.wisc.edu/~remzi/OSTEP/threads-intro.pdf)。

## 机制二：调度把并发变成具体的执行顺序

在单个处理核心上，多个任务可以交替推进，形成并发。
在多核心上，部分任务可能真正同时执行，形成并行。
是否并行还受运行时、任务依赖和资源竞争约束，创建线程本身不能保证加速。

当一个线程发起需要等待的读取，它可能进入阻塞状态。
操作系统可以把处理器交给其他就绪任务；读取完成后，等待者重新具备运行条件，仍要等调度。
所以“CPU 不忙”不一定表示系统没有工作，也可能表示关键任务正在等数据。

为了让某个任务不能永远独占处理器，系统可以在适当时机中断它，保存寄存器与执行位置，再恢复其他任务。
调度策略在响应速度、公平与吞吐之间做选择，上下文切换本身也有成本。
线程数量远多于实际可用资源时，更多切换与竞争可能抵消收益。

## 机制三：虚拟内存首先是一种地址抽象

两个进程都可以使用相同的虚拟地址，却对应不同的物理位置。
操作系统与硬件合作完成映射和权限检查，让程序不必直接管理整台机器的物理布局。
地址抽象与隔离目标见 [OSTEP：Address Spaces](https://pages.cs.wisc.edu/~remzi/OSTEP/vm-intro.pdf)。

因此，“虚拟内存”不等于“把硬盘当内存”。
利用持久存储暂存部分内存内容，只是某些内存管理机制的一部分。
即使没有发生换出，地址映射与进程间隔离仍然有意义。

隔离也有明确范围：线程共享同一进程地址空间时，一个线程错误修改对象，其他线程可能同时受到影响。
而进程隔离也不能消除 CPU、内存容量和磁盘等共享资源上的竞争。
需要根据故障边界和数据交换成本选择结构。

## 机制四：文件和 I/O 把设备细节收在接口后面

应用可以请求打开文件、读取字节和关闭资源，而不必直接控制 SSD 的内部操作。
文件系统管理名称、目录、内容位置和相关元数据；应用仍要负责解释文件中的格式。
对文件系统来说，一段坐标表和一张图像首先都可以是字节序列。
参见 [OSTEP：Files and Directories](https://pages.cs.wisc.edu/~remzi/OSTEP/file-intro.pdf)。

应用通常通过系统调用请求这些服务，由内核检查权限并协调设备。
读写接口可能阻塞调用者，也可能提供异步完成方式；异步改变等待和组织工作的方式，不会让存储介质瞬间变快。
若生产图像的速度长期大于写盘速度，队列最终仍会增长。

还要区分“写入调用返回”与“数据已经持久保存”。
系统可能先把数据缓存在内存中，再写入设备；需要持久性时，还涉及刷新、文件系统与设备保证。
OSTEP 的文件章节专门讨论 `fsync`，并说明文件内容与目录项都可能需要考虑。

## 机制五：共享数据为什么会丢更新

假设计数初始为零，两个线程都要执行“读取、加一、写回”。
若两个线程先后都读到零，然后各自写入一，最终结果就是一，而不是二。
问题在于整个复合操作被穿插；源代码只有一行，也不自动获得所需的原子性。

互斥锁可以把整个读改写过程放进临界区，让其他遵守同一把锁的线程等待。
只锁住最后的写回，仍可能保留前面“都读到旧值”的问题。
锁的正确使用还要求共享数据的所有相关访问都遵守相同协议。

锁也会引入等待：若任务甲持有锁 A 等锁 B，任务乙持有锁 B 等锁 A，就可能死锁。
固定获取顺序、减少持锁范围、采用明确的消息传递方式，都是可分析的设计选择。
这里的互斥不等于崩溃后的持久性，也不能直接替代数据库事务。

## 建筑类比：共享现场与资源预约

进程像有边界的作业区域，线程像区域内的作业班组，调度像安排有限设备的使用顺序。
多人修改同一份设备台账，需要约定谁在什么时候可以更新，就像临界区。
**类比边界：**程序的交错可能发生得极细，不能凭“大家大概不会同时做”保证正确；机器需要明确协议。

## 最小实验：交错读写与加锁

前半段手工模拟一种丢更新顺序，后半段用真实线程和同一把锁计数。
手工模拟避免把某次运行中“恰好没有撞上”误认为没有竞争。

```python
from threading import Lock, Thread

value = 0
read_a = value
read_b = value
value = read_a + 1
value = read_b + 1
print("交错结果：", value)

counter = [0]
lock = Lock()
def worker():
    for _ in range(1000):
        with lock:
            counter[0] += 1

threads = [Thread(target=worker) for _ in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
print("加锁结果：", counter[0])
```

预期输出：

```text
交错结果： 1
加锁结果： 2000
```

例子验证的是计数协议，不测并行速度；删除锁后是否立刻出错，还取决于运行时与实际调度。

## 闭卷检查：先预测，再解释

1. **预测：**两个线程都读到十，各自加一并写回，按上述交错顺序最后是多少？
2. **解释：**一个程序卡住但 CPU 使用率很低，为什么不能直接判断“处理器太弱”？
3. **迁移：**若视频采集速度持续高于分析速度，单纯不断新增线程能解决什么，又留下什么？

<details>
<summary>答案要点与常见误区</summary>

1. 最后是十一，发生了一次更新覆盖；正确累计应是十二。
2. 程序可能在等网络、存储、锁或其他任务，应先观察等待原因和资源路径。
3. 若尚有可用资源，并发可能改善吞吐；若已经达到瓶颈，仍需限制队列、降低输入、丢弃可丢帧或增加有效处理能力。

常见误区：线程越多越快；共享地址空间代表没有独立状态；虚拟内存只是交换文件。
另一个误区是“写成功就一定抗断电”，以及“某次并发测试没错就证明没有竞争”。

</details>
